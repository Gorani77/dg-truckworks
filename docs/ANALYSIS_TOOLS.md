# 읽기 전용 분석 도구

작성일: 2026-10-10 (Asia/Seoul)  
상태: 코드·문서 작성 완료, 사용자 확인 대기. 테스트·빌드·린트·설치·서버 실행·HTTP 요청·브라우저 검증은 수행하지 않았다.

## 이번 범위

계획 단계 4의 첫 작업으로 공장 현황·설비·이벤트·대기열·부품 이력 조회 도구를 작성했다. LLM·LangGraph 질문 분석은 아직 연결하지 않았다. 화면의 조회 버튼은 서버 도구를 직접 호출한다. 자연어 질문과 분석 요청은 계속 비활성이다. 새 의존성이나 DB 마이그레이션은 없다. 이전 PostgreSQL 작업의 설치가 아직이면 HISTORY_STORAGE.md를 먼저 따른다.

도구는 현재 서버 메모리의 실행만 읽는다. DB가 비활성화돼 있어도 사용할 수 있다. 과거 실행은 기존 생산 이력 화면에서 읽는다. 도구에 생산 시작·정지·복구나 임의 SQL·명령 실행 기능은 없다. 재고 부족·병목 원인을 확정하거나 LLM 응답처럼 설명하지 않는다.

## API와 입력

`GET /api/analysis/tools/{tool_name}?expected_run_id={현재 실행 UUID}`

| 도구 | 선택/필수 입력 | 반환 자료 |
|---|---|---|
| get_factory_state | 추가 필터 없음 | 공장 전체 스냅샷 |
| get_station_status | station_id 필수 | 선택 설비의 상태·부품·잔여시간 |
| get_recent_events | station_id·part_id 선택, limit 기본20/최대100 | 필터에 일치하는 최근 이벤트, 전체 일치 수, 생략 여부 |
| get_buffer_status | station_id 선택 | 소재 잔여와 설비별 입력 대기·예약·빈 자리 |
| get_part_history | part_id 필수, limit 기본20/최대100 | 현재 실행 부품 상태와 해당 부품의 최근 이벤트 |

`expected_run_id`는 필수다. 초기화 뒤 이전 실행 ID를 보내면409다. 허용하지 않은 도구·잘못된 UUID·limit 범위·필수 필터 누락·지원하지 않는 필터 조합은422, 존재하지 않는 설비/부품은404다. 부품 이력은 설비 필터를 받지 않는다. limit는 이벤트 도구에서만 의미가 있다. 빈 최근 이벤트 결과는 정상이며 없는 부품을 존재하는 부품으로 만들어 반환하지 않는다.

응답의 공통 필드:

- tool_name: 실제 호출한 도구.
- source: live_memory. DB 커밋 완료나 과거 이력 조회를 뜻하지 않는다.
- observed_at: 서버에서 조회한 UTC 실제 시각. 화면에서는 Asia/Seoul로 표시한다.
- run_id·state_version·last_event_sequence·simulation_time_seconds: 결과의 기준 상태.
- data: 도구별 구조화 자료. 이벤트는 최근 N개를 순번 오름차순으로 돌려준다. truncated=true면 이전 일치 이벤트가 생략됐다.

단독 ST-01 엔진은 부품을 설비 안에만 보관하므로 get_part_history의 part가null일 수 있다. 실제 부품 ID와 이벤트는 그대로 반환한다. 부품 없는 설비 고장 이벤트는 part_id=null이며 설비 최근 이벤트에서 볼 수 있다.

## 데이터 흐름

AgentPanel → useAnalysisTools → api/analysis.ts → analysis route → ReadContext → execute_tool → 구조화 응답 순서다. 입력/출력 Pydantic 모델과 허용된 도구 이름은 backend/src/truckworks/agents/tools.py에 있다. 후속 에이전트도 이 읽기 경계를 재사용할 수 있다.

라우트에서 같은 이벤트 루프 안에 await 없이 불변 스냅샷과 이벤트 튜플을 함께 읽는다. 도구가 공장 시계를 강제로 진행시키지 않는다. 이벤트는 그 실행 ID와 마지막 이벤트 순번까지 제한한다. 각 호출은 별도 관측이며 연속 호출들이 항상 같은 상태 버전일 것이라고 가정하면 안 된다.

화면은 수동 조회 결과의 시각·버전·실행을 표시한다. 다른 설비를 선택해도 이전 결과의 데이터는 그 조회 시점 자료다. 다시 버튼을 눌러 새로 조회한다. 초기화로 실행 ID가 바뀌면 패널을 다시 만들어 이전 결과를 지우고 이전 요청을 취소한다. 요청 제한 시간은5초이며 실패 시 버튼으로 재시도한다. 자동 재전송은 하지 않는다.

## 사용자가 직접 확인할 절차

기존 안내대로 백엔드를 재시작하고 프론트엔드 화면을 새로고침한다.

1. READY 상태에서 운영 분석의 공장 현황을 누른다. 실제 현재 실행 ID·READY·소재20·수량0이 기대 결과다. 조회 자체로 생산이 시작되면 안 된다.
2. 생산 중 설비를 선택해 설비 상태·대기/예약·최근 이벤트를 각각 조회한다. 선택한 설비 ID와 조회 결과가 일치해야 한다. 공장 시계는 원래 실행에 따라 계속 진행한다.
3. 설비 고장 후 설비 상태를 조회한다. FAULTED·고장 전 상태·현재 부품·잔여시간이 보이고 고장 이벤트의 순번을 읽을 수 있어야 한다. 도구 조회로 고장이 복구되면 안 된다.
4. 20개 생산에서 입력 대기+예약≤3, 빈 자리=입력 용량-대기-예약인지 확인한다. 처리 중 부품은 입력 대기 수량에 더하지 않는다.
5. 부품을 골라 이력을 조회한다. 이벤트의 부품 ID가 선택한 부품과 같고 순번 오름차순이어야 한다. 단독 ST-01도 실제 설비 내 부품을 선택할 수 있어야 한다. part=null의 설명도 확인한다.
6. API 문서에서 get_recent_events를 limit=1로 조회한다. 일치 이벤트가 여러 개면 가장 최근1개·truncated=true·정확한 matched_count가 기대 결과다. 부품 없는 고장도 필터 없는 설비 조회에는 포함돼야 한다.
7. 이전 실행 UUID로 초기화 후 요청하면409, 없는 설비/부품404, limit=0/101·없는 도구·필수 필터 누락422를 확인한다. 정상적인 빈 최근 이벤트는200이다.
8. 빠른 초기화·조회 실패 후 다시 조회를 확인한다. 새 실행에 이전 응답이 혼입되지 않아야 한다. 서버 중단 때 오류·재시도 안내가 보여야 한다.
9. 이전 저장/생산 기능의 미확인 항목은 기존 안내대로 별도 확인한다. 이번 코드 작성으로 확인 완료 처리하지 않는다.
