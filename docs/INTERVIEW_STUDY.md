# TruckWorks 개발 순서대로 배우는 학습 노트

작성·갱신일: 2026-10-11 (Asia/Seoul)

이 문서는 TruckWorks를 처음 만들기 시작한 시점부터 실제 개발 흐름을 따라가는 공부 자료다. 앞 장에서 만든 것이 왜 다음 작업으로 이어지는지 이해하는 것을 목표로 한다. 면접 답변은 각 단계의 내용을 이해한 뒤 자신의 말로 설명하는 연습에 사용한다.

날짜별 작업 사실은 [PROGRESS.md](C:/project/truckworks/docs/PROGRESS.md), 현재 목표와 범위는 [PROJECT_PLAN.md](C:/project/truckworks/PROJECT_PLAN.md)에 있다. 이 문서는 같은 작업에 대해 “왜 필요했고, 무엇을 배워야 하는가”를 풀어 설명한다. 앞으로 개발한 단위마다 다음 장을 추가한다.

기존 작업 기록과 현재 코드를 바탕으로 학습 단계를 구성했다. 같은 구현 작업 안에서 파일을 작성한 세부 순서는 별도 기록이 없으므로, 그 안에서는 이해하기 쉬운 코드 읽기 순서로 설명한다. 코드 설명과 사용자 실행 확인 결과는 구분한다.

## 전체 학습 순서

1. 만들 서비스와 첫 공개 범위를 정한다.
2. React 프론트엔드 프로젝트를 만든다.
3. 첫 관제 화면과 공정 선택을 구현한다.
4. 화면을 컴포넌트·데이터·상태 로직으로 나눈다.
5. 다크 테마와 Pretendard를 적용한다.
6. Python 백엔드 프로젝트와 가상환경을 만든다.
7. src 패키지를 구성하고 설치·import한다.
8. 공장 규칙을 Python 데이터 구조로 표현한다.
9. 초기 공장 상태를 생성한다.
10. FastAPI 앱과 상태 수명을 구성한다.
11. 공장 상태를 HTTP API로 제공한다.
12. 로컬 서버를 실행하고 발생한 문제를 이해한다.
13. SimPy로 첫 설비의 소재 1개를 처리하고 API에서 진행 상태를 제공한다.
14. 관제 화면에서 서버 상태·시작 명령·생산 이벤트를 연결한다.
15. 기본 3D 공장 장면에 설비 선택과 실제 서버 상태를 표현한다.
16. 사용자 화면에서 발견된 3D 영역 크기 문제를 수정한다.
17. 사용자 A안 선택에 따라 코드 모델을 공정별 외형으로 구분한다.
18. 이동 1초를 확정하고 같은 차체 1개를 전체 공정에 연결한다.
19. 실행 시계를 분리하고 일시정지·재개·초기화를 API와 화면에 연결한다.
20. 소재 20개를 동시에 흐르는 FIFO 생산라인으로 확장한다.
21. 설비 고장 시 남은 가공을 보존하고 복구 후 이어간다.
22. PostgreSQL에 실행·부품·이벤트 이력을 저장한다.
23. 현재 관제와 구분해 저장된 실행·부품 이벤트를 조회한다.
24. 현재 실행을 읽는 분석 도구를 만들고 수동 조회 화면으로 연결한다.
25. OpenAI와 LangGraph를 연결해 질문에서 도구 선택·근거 설명으로 이어간다.
26. 분석 성공·실패 이력과 확인된 부분 사용량을 저장하고 다시 조회한다.
27. HTTP 반복 조회를 WebSocket 상태·이벤트 수신과 자동 재연결로 바꾼다.
28. 방문자별 생산 엔진과 저장 이력의 소유권을 연결한다.
29. 사용 중인 연결과 요청을 보호하면서 유휴 공장을 정리한다.
30. 현재 코드 범위를 로컬 데모 소개와 실제 시연 안내로 정리한다.

4~5단계는 같은 구조 개선 작업이고, 8~11단계는 같은 API 구현 작업이다. 학습할 때는 순서대로 읽되 실제로 별개 배포나 확인을 거쳤다고 해석하지 않는다.

## 1단계. 무엇을 만들지 먼저 정하기

### 그때 필요했던 것

“공장 시뮬레이터”만으로는 개발 범위가 너무 넓다. 어떤 제품을 만들고, 어디까지 보여줄지 정해야 화면과 데이터에 무엇이 필요한지 알 수 있다.

### 실제로 정한 내용

첫 공개는 차체 생산라인과 읽기 전용 분석 에이전트다. 트럭 전체 조립 대신 단순화한 프레임형 차체 하나를 생산 부품으로 취급하기로 했다. 차체 크기는 180 × 60 × 12 mm, 기본 소재는 20개다. 공정 처리시간은 2·8·6·4·2초로 정했다.

이 값은 실제 공장의 측정 자료가 아니라 이 프로젝트의 시뮬레이션 가정이다. 설비당 동시 처리 1개·입력 대기 3개, 고장 복구 후 남은 작업 이어하기, 불량률 5% 같은 규칙도 합의했다. 규칙을 결정한 것과 동작을 구현한 것은 다르다.

### 여기서 배우는 개념

**범위 설정**은 이번 버전에서 해결할 문제를 제한하는 일이다. **명세**는 기능이 어떤 규칙으로 동작해야 하는지 적은 것이다. “고장이 나도 복구하면 이어서 처리한다”가 명세라면, 남은 시간을 보관하고 복원하는 코드는 구현이다.

관련 문서: [제품·공정 명세](C:/project/truckworks/docs/PRODUCT_PROCESS_DRAFT.md), [기술 구성](C:/project/truckworks/docs/TECH_STACK_DRAFT.md).

### 직접 설명해 보기

“왜 처음부터 트럭 전체를 조립하지 않았나요?”

차체 하나의 투입·처리·검사·저장 흐름을 먼저 연결하면 작은 범위에서도 생산과 분석을 보여줄 수 있기 때문이다. 이후 확장할 수 있지만 첫 단계부터 모든 부품을 모델링할 필요는 없다.

### 다음 작업으로 이어지는 이유

생산 대상과 공정이 정해졌으므로 사용자가 이를 볼 수 있는 프론트엔드부터 만들었다.

## 2단계. React 프론트엔드 프로젝트 만들기

### 그때 필요했던 것과 실제 작업

브라우저에서 관제 화면을 보여줄 기반이 필요했다. 사용자가 `C:\project\truckworks\frontend`에 React + TypeScript + Vite 프로젝트를 생성했다. 생성된 설정은 ESLint를 사용한다. 이후 기본 예제 파일을 바탕으로 관제 화면을 구현했다.

### 여기서 배우는 개념

- **React**: 화면을 컴포넌트로 구성하고 상태 변화에 맞춰 표시를 갱신하는 라이브러리다.
- **TypeScript**: 코드 작성·검사 과정에서 데이터 형태와 타입의 불일치를 찾는 데 도움을 준다. 서버 JSON이 타입에 맞는지 실행 중 자동 검사해 주는 것은 아니다.
- **Vite**: 개발 서버와 프론트엔드 빌드에 사용하는 도구다.
- **ESLint**: 코드의 문제 패턴을 검사하는 도구다. 실제 기능 동작 확인을 대신하지 않는다.
- **npm**: 프론트엔드 패키지 관리와 프로젝트 스크립트 실행에 사용한다.

### 코드 읽기

[package.json](C:/project/truckworks/frontend/package.json)을 먼저 읽는다. `dependencies`에서 앱이 사용하는 패키지를, `devDependencies`에서 개발·빌드 도구를 본다. `scripts.dev`의 `vite`가 `npm run dev`로 실행되는 명령이다.

현재 진입 흐름은 다음과 같다.

```text
frontend/index.html의 root 요소
  → src/main.tsx가 React 화면을 연결
  → App.tsx
  → app/FactoryDashboard.tsx
```

[main.tsx](C:/project/truckworks/frontend/src/main.tsx)의 `createRoot(...).render(...)`는 React 화면을 HTML의 지정된 위치에 연결한다. 현재처럼 App에서 대시보드를 연결하는 구조는 뒤의 구조 개선 단계에서 정리됐다.

### 직접 설명해 보기

“React와 Vite는 같은 역할인가요?”

React는 화면을 구성하고 갱신하는 데 사용하고, Vite는 개발 서버와 빌드 환경을 제공한다. 화면 라이브러리와 개발 도구의 역할이 다르다.

### 다음 작업으로 이어지는 이유

프로젝트 기본 예제가 생겼으므로 이를 공장 관제 화면으로 바꿀 수 있었다.

## 3단계. 첫 관제 화면과 공정 선택 만들기

### 그때 필요했던 것

사용자가 어떤 정보를 보고 어떤 조작을 할지 화면으로 구체화할 필요가 있었다. 아직 서버와 생산 엔진은 없었다.

### 실제로 한 작업

처음에는 `App.tsx`, `App.css`, `index.css` 중심으로 상단 현황, 좌측 제어·공정 목록, 중앙 공장 배치, 우측 상세·에이전트, 하단 이벤트 영역을 구성했다. 공정을 선택하면 목록과 중앙 선택 표시, 우측 상세 정보가 함께 바뀌도록 했다.

첫 화면은 밝은 스타일과 정적인 배치 미리보기였다. 뒤에서 다크 테마와 SVG 배치도로 개선했다. 이때도 실제 Three.js 3D나 생산 동작을 구현한 것은 아니다. 실제 데이터가 없는 수치는 `—`로, 연결 전 기능은 비활성화 상태로 표시했다.

### 여기서 배우는 개념: 상태와 표시

현재 선택한 공정 ID는 **UI 상태**다. 사용자가 선택을 바꾸면 이 값이 바뀌고, 화면은 해당 공정의 정보를 표시한다. 공정의 이름과 기본 처리시간은 선택에 따라 변하는 값이 아니라 미리 정의한 데이터다.

현재 코드에서 이 흐름을 따라가면 다음과 같다.

```text
공정 버튼 클릭
  → selectStation(id)
  → selectedId 갱신
  → 해당 ID의 공정 찾기
  → 목록·배치도·상세 정보에 같은 선택 전달
```

같은 선택을 사용하는 영역이 각자 별도의 선택 상태를 가지면 목록과 상세가 다른 공정을 보여줄 수 있다. 그래서 대시보드가 선택 상태를 사용하고 필요한 값을 하위 컴포넌트에 전달한다.

### 코드 읽기

현재 구현은 [선택 훅](C:/project/truckworks/frontend/src/features/factory/hooks/useStationSelection.ts), [대시보드](C:/project/truckworks/frontend/src/app/FactoryDashboard.tsx)에서 읽는다. 당시의 큰 App 파일은 구조 개선으로 바뀌었으므로 현재 파일과 최초 구현을 혼동하지 않는다.

### 직접 설명해 보기

“공정을 클릭했을 때 생산 상태가 바뀌나요?”

현재는 어느 공정을 보고 있는지 나타내는 UI 선택만 바뀐다. 설비 가동이나 부품 생산 같은 서버 상태 변경은 아직 연결하지 않았다.

### 다음 작업으로 이어지는 이유

화면 영역과 상호작용이 늘어나면서 하나의 App 파일에서 모두 관리하기보다 역할별로 나눌 필요가 생겼다.

## 4단계. 동작하는 화면을 유지하며 코드 나누기

### 그때 필요했던 것과 실제 작업

사용자가 가독성·유지보수성·확장성을 위해 파일과 컴포넌트를 분리해 달라고 요청했다. 화면을 영역별로 나누고 데이터·타입·선택 로직도 JSX와 분리했다.

| 위치 | 옮긴 책임 |
|---|---|
| `frontend/src/App.tsx` | 화면 진입과 연결 |
| `frontend/src/app/` | 전체 대시보드 조합과 헤더 |
| `frontend/src/features/factory/` | 공정 데이터·타입·선택 훅·공장 화면 영역 |
| `frontend/src/features/agent/` | 에이전트 영역 |
| `frontend/src/scene/` | 작업 영역과 배치도 표현 |
| `frontend/src/components/` | 공통 Panel·Button |

### 여기서 배우는 개념

**컴포넌트**는 화면의 의미 있는 영역을 표현한다. 설비 상세와 이벤트 목록처럼 책임이 다른 영역을 나누면 해당 영역을 수정하기 쉽다. 단순히 파일 길이를 줄이려고 모든 태그를 별도 컴포넌트로 만드는 것은 아니다.

**props**는 부모가 자식에게 전달하는 데이터와 함수다. 대시보드는 선택한 설비를 상세 영역에 전달하고, 목록에는 선택 함수를 전달한다.

**커스텀 훅**은 React 상태 로직을 함수로 묶은 것이다. 현재 `useStationSelection`은 선택 ID와 선택 처리 방법을 묶는다. 현재 사용처 하나의 로직을 읽기 쉽게 분리한 것이며, 재사용 횟수가 많다고 주장할 필요는 없다.

선택 ID만 상태로 저장하고 선택한 공정 객체는 목록에서 찾는다. 같은 정보를 ID와 객체 두 군데에 따로 저장하면 서로 어긋날 가능성이 있어 현재는 ID를 기준으로 필요한 값을 구한다.

## 5단계. 다크 테마와 Pretendard 적용하기

### 실제로 한 작업

사용자 요청으로 밝은 스타일에서 기본 다크의 산업 관제 스타일로 변경했다. Pretendard, 절제된 황색 선택 강조, 각진 패널과 정보 위계를 적용했다. 장식적인 카드보다 공장 작업 영역과 공정 정보를 중심으로 배치했다.

### 여기서 배우는 개념

## 7단계. src 패키지 구성과 설치·import

### 실제로 한 작업

`backend/src/truckworks`와 그 아래 API·도메인·시뮬레이션·에이전트·저장 패키지 위치를 추가했다. 프로젝트 이름을 `truckworks`로 맞추고 Hatchling 빌드 설정과 패키지 경로를 선언했다.

```toml
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]

```

위 코드는 현재 [pyproject.toml](C:/project/truckworks/backend/pyproject.toml)의 관련 부분이다. FastAPI 의존성은 다음 API 작업에서 추가됐다.

### 여기서 배우는 개념

`src`는 소스를 담는 상위 폴더이고 `truckworks`가 import할 패키지 이름이다. `__init__.py`를 두어 일반 Python 패키지로 구성했다. 시뮬레이션·에이전트 폴더가 있다고 기능이 구현된 것은 아니다.

uv는 프로젝트 환경과 의존성을 관리하고, Hatchling은 프로젝트 패키지 빌드에 사용한다. `uv sync`는 선언과 잠금 파일을 바탕으로 환경을 맞추는 명령이다. `uv.lock`에는 해석된 구체적인 버전이 기록된다. 선언 파일과 설치 결과는 구분한다.

### 이 단계에서 실제 겪은 문제

PowerShell에서 `uv` 명령을 찾지 못했다. PyCharm에 표시된 실행 파일 위치를 바탕으로 전체 경로를 사용했다.

```powershell
& "$env:APPDATA\Python\Scripts\uv.exe" sync
& "$env:APPDATA\Python\Scripts\uv.exe" run python -c "import truckworks; print(truckworks.__file__)"
```

작업 위치는 `C:\project\truckworks\backend`다. `&`는 PowerShell에서 지정한 실행 파일을 호출하는 연산자다. 전체 경로를 사용해 도구를 호출한 것이며 PATH 설정 자체를 수정한 것은 아니다.

사용자가 공유한 결과는 `truckworks==0.1.0` 설치와 다음 import 경로였다.

```text
C:\project\truckworks\backend\src\truckworks\__init__.py
```

이 결과로 패키지 설치와 src 경로 import를 확인했다. 이후 추가한 API 의존성까지 이 시점에 확인한 것은 아니다.

### 실제로 한 작업

### 여기서 배우는 개념: 정의와 상태

`StationDefinition`은 어떤 설비인지를 나타낸다. 예를 들어 성형 설비의 기본 처리시간은 8초다. `StationSnapshot`은 현재 무엇을 하는지 나타낸다. 처리 중 부품, 대기 부품, 남은 처리시간이 들어간다.

8초짜리 설비에서 부품을 5초 처리했다면 정의의 처리시간은 여전히 8초이고 상태의 남은 시간은 3초가 되는 식이다. 이 예시는 의미를 설명하기 위한 것이며 현재 시간이 진행되는 코드는 없다.

**dataclass**는 이런 데이터를 필드로 표현하기 위해 사용한다. 도메인에는 FastAPI나 DB 모델을 직접 넣지 않아 생산 데이터 표현을 HTTP 처리에서 분리했다.

`frozen=True`는 일반적인 속성 재할당을 막고, `slots=True`는 정해진 속성으로 객체 구조를 제한한다. frozen이 모든 중첩 데이터의 불변성이나 동시성 안전을 자동 보장하지는 않는다. 성능 개선 수치도 측정하지 않았다. [Python dataclass 공식 문서](https://docs.python.org/3/library/dataclasses.html)

타입 힌트만으로 생성 시 값 범위가 자동 검사되지는 않는다. 음수 수량이나 잘못된 상태 전이는 별도 규칙으로 다뤄야 한다.

## 9단계. 초기 공장 스냅샷 만들기

### 실제로 한 작업

[factory.py](C:/project/truckworks/backend/src/truckworks/domain/factory.py)에 `create_initial_factory()`를 작성했다. 스냅샷은 특정 시점의 상태를 묶어 표현한 데이터다.

| 값 | 초기 상태 |
|---|---|
| 실행 상태 | READY |
| 소재 | 20개 |
| 양품·불량·처리 중·대기 수량 | 각각 0 |
| 설비 | 5개, 모두 IDLE |
| 시뮬레이션 시간 | 0초 |
| 실행 ID·생성 시각 | 새 UUID·현재 UTC 시각 |
| 상태 버전·마지막 이벤트 순번 | 각각 0 |

### 여기서 배우는 개념

**실행 ID**는 어느 공장 실행인지 구분한다. 브라우저 요청마다 바꾸려는 값이 아니다. **생성 시각**은 실행을 만든 현실 시각이고, **시뮬레이션 시간**은 모델 안에서 흐른 시간이다. 지금은 전자만 생성되며 후자는 0이다.

`schema_version`은 응답 형식, `model_version`은 생산 모델 규칙의 버전을 나타내려는 값이다. `state_version`과 `last_event_sequence`는 이후 상태 변경과 이벤트 순서를 표현하기 위한 필드지만, 증가·충돌 검사·이벤트 기록은 아직 없다.

불량률 0.05와 시드 42도 설정만 있다. 실제 난수 판정은 없다. 추후 같은 시드를 사용해도 재현성을 확보하려면 입력과 난수 호출 순서 같은 조건이 같아야 한다.

### 직접 설명해 보기

“UUID나 버전 필드가 있으면 중복 실행과 충돌이 방지되나요?”

아니다. 현재는 식별과 버전 표현을 위한 데이터다. 중복 방지와 충돌 처리는 실제 명령 처리 규칙을 구현해야 한다.

초기 공장을 언제 만들고 어디에 보관할지 정해야 요청마다 같은 공장을 조회할 수 있다.

## 10단계. FastAPI 앱과 공장 상태의 수명 구성하기

### 실제로 한 작업

[app.py](C:/project/truckworks/backend/src/truckworks/api/app.py)에 `create_app()`과 lifespan을 작성했다. [settings.py](C:/project/truckworks/backend/src/truckworks/settings.py)에서 환경 설정을 읽고 CORS를 연결했다.

```python
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.factory_snapshot = create_initial_factory()
    try:
        yield
    finally:
        del app.state.factory_snapshot
```

### 여기서 배우는 개념

**앱 팩토리**는 앱을 만들어 반환하는 함수다. **lifespan**은 앱의 시작 준비와 종료 정리를 묶는다. 위 코드에서 `yield` 이전은 요청을 받기 전 준비, `finally`는 종료 정리다. 초기 공장은 이때 한 번 만들어 앱 메모리에 보관한다. [FastAPI lifespan 공식 문서](https://fastapi.tiangolo.com/advanced/events/)

요청마다 새 공장을 만들면 실행 ID와 생성 시각이 계속 바뀐다. 나중에 생산이 진행되는 상태를 유지할 수도 없다. 그래서 요청은 기존 상태를 읽도록 했다.

현재 보관 위치는 메모리다. 서버 재시작 시 새 초기 상태가 생기며 DB 복원은 없다. worker 프로세스를 여러 개 띄우면 각자 별도의 상태가 생긴다. 현재 구조를 그대로 확장 가능한 운영 저장소라고 설명하면 안 된다.

CORS는 서로 다른 출처의 브라우저 코드가 API 응답을 읽을 수 있도록 허용하는 설정이다. 프론트엔드의 5173 포트와 API의 8010 포트는 출처가 다르다. CORS는 사용자 인증이나 권한 검사를 대신하지 않는다.

### 직접 설명해 보기

“서버 재시작과 브라우저 새로고침은 어떤 차이가 있나요?”

브라우저 새로고침은 기존 서버에 다시 요청한다. 서버 재시작은 메모리 상태를 잃고 새 초기 공장을 만든다. 현재는 생산 로직이 없으므로 같은 서버를 조회해도 생산 시간은 계속 0이다.

### 다음 작업으로 이어지는 이유

앱이 공장을 보유하게 됐으므로 요청에서 이를 가져와 JSON으로 반환하는 경로를 연결했다.

## 11단계. 공장 상태를 HTTP API로 제공하기

### 실제로 한 작업

`GET /api/health`와 `GET /api/factory/state`를 추가했다. 라우터·의존성·응답 스키마를 나눴다.

```text
GET /api/factory/state
  → router가 공장 조회 함수 선택
  → Depends가 기존 공장 스냅샷 공급
  → Pydantic 응답 모델로 변환·검사
  → FastAPI가 JSON 응답 반환
```

### 코드 읽기 1: 기존 상태 가져오기

[dependencies.py](C:/project/truckworks/backend/src/truckworks/api/dependencies.py)의 `get_factory_snapshot()`은 `request.app.state.factory_snapshot`을 반환한다. `Depends`는 라우트에 필요한 값을 이 공급 함수에서 받도록 연결한다. 요청마다 공급 함수를 사용해도 공장을 새로 만드는 것은 아니다.

`Annotated`에는 타입과 의존성 정보를 함께 적는다. `cast(FactorySnapshot, ...)`는 타입 검사 도구에 타입을 알려 주며 실행 시 검사나 변환을 하지 않는다. [Python cast 공식 문서](https://docs.python.org/3/library/typing.html#typing.cast)

### 코드 읽기 2: 외부 응답 형식 정하기

[응답 스키마](C:/project/truckworks/backend/src/truckworks/api/schemas/factory.py)는 Pydantic 모델이다. 내부 생산 데이터는 dataclass로 표현하고 외부 응답은 별도 모델로 표현한다. 필드 관리 비용은 있지만 생산 데이터와 API 계약을 별도로 바꿀 수 있게 책임을 나눴다.

- `Field(ge=0)`: 0 이상.
- `Field(gt=0)`: 0 초과.
- `from_attributes=True`: 객체의 속성에서 값을 읽도록 허용.
- `model_validate(snapshot)`: 스냅샷을 응답 모델로 변환·검사.

개별 수량이 음수가 아니라는 것만으로 총수량 보존, 설비 용량 준수, 상태 전이의 정당성까지 검증되지는 않는다. 현재 설정은 모든 타입 변환을 금지하는 strict 모드도 아니다.

### 코드 읽기 3: 라우트에서 응답하기

### 새 개념: SimPy 시간과 현실 시간

SimPy의 Environment는 시뮬레이션 이벤트를 관리한다. `env.process(...)`는 generator를 프로세스로 등록하고, `yield env.timeout(2)`는 시뮬레이션 안에서 2초 뒤 이벤트까지 해당 공정 처리를 멈춘다. 이 문장만으로 현실에서 2초를 기다리는 것은 아니다. [SimPy 기본 개념](https://simpy.readthedocs.io/en/stable/simpy_intro/basic_concepts.html)

runner는 asyncio task에서 약 0.1초마다 단조 시계의 경과 시간을 읽어 엔진에 전달한다. 단조 시계는 달력 시각 보정과 관계없이 경과 시간을 계산하는 데 사용한다. 현실의 스케줄링 지연 때문에 정확히 매 0.1초 실행된다고 보장하지 않으며, 횟수에 0.1을 더하는 대신 실제 경과 시간을 사용한다.

엔진은 목표 시간 이하인 이벤트를 `peek()`와 `step()`으로 처리한다. 따라서 정확히 2초에 예약된 완료 이벤트도 포함한다. 이벤트 사이의 남은 시간은 경과 시간으로 계산하므로 SimPy의 이벤트 시각인 `env.now`와 응답의 진행 시간이 항상 같지는 않다. 완료 후에는 2초에서 고정한다. [SimPy Environment](https://simpy.readthedocs.io/en/stable/api_reference/simpy.core.html)

### 코드 읽기와 데이터 흐름

```text
POST /api/factory/single-station/start + expected_run_id
  → 라우트가 runner를 주입받음
  → engine.start가 현재 실행 ID와 READY 검사
  → SimPy 프로세스 등록·t=0 이벤트 처리
  → 소재 19·부품 ID 생성·PROCESSING·시작 이벤트
  → runner가 실제 경과 시간을 전달
  → timeout(2) 처리·완료 이벤트
  → PAUSED·BLOCKED·남은 시간 0

GET /api/factory/state → 현재 스냅샷 → Pydantic → JSON
GET /api/factory/events → 현재 실행 이벤트 → Pydantic → JSON
```

`single_station.py`의 `_process_material()`에서 시작 전후 두 번의 스냅샷 교체를 읽고, `_record()`에서 이벤트 순번이 증가하는 흐름을 본다. `runner.py`에서는 await로 기다리는 동안 HTTP 요청을 받을 수 있다는 점을 읽는다. 같은 이벤트 루프에서 시작 경로에는 await가 없으므로 중복 요청이 상태 검사와 소재 소비 사이에 끼어들지 않는다. 여러 프로세스 간 공유나 DB 트랜잭션까지 해결한 것은 아니다.

GET은 현재 상태를 읽기만 한다. 조회하지 않아도 runner가 처리한다. 불변 스냅샷을 교체하므로 응답 작성 중 이전 스냅샷의 필드 일부만 바뀌지 않는다. state_version은 진행 상태 갱신마다 증가하고 last_event_sequence는 시작·완료 이벤트가 생길 때만 증가한다. 둘을 같은 수로 해석하지 않는다.

### 완료 부품과 수량을 읽는 법

2초 후의 완료는 소재 투입 공정 완료다. 다음 공정 전달은 아직 없으므로 부품 ID를 현재 설비에 유지하고 BLOCKED로 표시한다. 실제 입력 대기열이 가득 찬 상황까지 구현한 것은 아니다. 이번 단일 처리 범위가 끝나면 자동 PAUSED로 멈추며, 사용자 일시정지·재개 명령은 아직 없다.

소재 19개 + 라인 내부 부품 1개 = 초기 20개다. in_process_count는 라인 내부의 완료 대기 부품도 포함해 1을 유지하고, waiting_count는 입력 대기열이므로 0이다. 검사·적재 전이므로 good_count와 rejected_count는 모두 0이다. 완료 이벤트를 양품 생산으로 해석하면 안 된다.

### 새 개념: 조회 반복과 React effect 수명

현재 연결은 WebSocket이 아니라 HTTP 조회 반복이다. 상태 GET과 이벤트 GET이 끝난 뒤 300ms 후 다음 조회를 예약한다. 고정 간격마다 요청을 겹쳐 보내지 않는다. 실패 시에는 1.5초 후 다시 시도한다. 이 간격은 UI 조회 간격이며 서버의 시뮬레이션 처리시간을 바꾸지 않는다.

effect는 화면이 살아 있는 동안 조회를 시작하고 cleanup에서 AbortController와 타이머를 정리한다. 단순히 화면을 떠났다고 이미 보낸 서버 명령이 되돌려지는 것은 아니다. 시작 POST의 응답을 못 받았을 때 자동 재전송하지 않고 상태 조회를 재개하는 이유도 여기에 있다.

Vite 개발 프록시는 브라우저가 같은 출처의 /api를 호출하면 개발 서버에서 8010 백엔드로 전달한다. 이번 프록시는 개발 환경 설정이며 배포 환경의 라우팅까지 구성한 것은 아니다. 설정 변경 후에는 프론트엔드 개발 서버를 다시 실행한다.

### 데이터 흐름과 서로 다른 상태

```text
화면 진입
  → useFactoryConnection
  → GET state → GET events
  → 같은 run_id·상태의 이벤트 순번 이하만 선택
  → 서버 정의 변환 → 대시보드가 현황·상세·이벤트에 전달

시작 버튼
  → 현재 run_id + POST single-station/start
  → 서버 응답 표시 → 조회 재개
  → 서버 runner가 시간을 진행 → 다음 조회에 남은 시간·완료 이벤트 표시
```

현재 선택 ID는 UI 상태, READY/RUNNING/PAUSED는 서버 실행 상태, 연결 중/연결됨/연결 끊김은 통신 상태다. 서버가 PAUSED여도 연결은 정상일 수 있다. 서버 연결 오류를 생산 고장으로 해석하지 않는다.

서버 정의는 snake_case이고 기존 화면 모델은 camelCase다. presentation.ts에서 둘을 연결해 기존 목록·배치도 컴포넌트의 책임을 유지했다. TypeScript 타입 선언은 수신 JSON의 런타임 스키마 검사와 다르다. 이번에는 자체 백엔드 계약을 사용하며 완전한 런타임 응답 검사를 추가하지 않았다.

### 오래된 응답과 수신 실패 처리

시작 시 진행 중 조회를 취소하고, 명령 요청 중에는 조회를 멈춘다. 시작 전 응답이 시작 후 상태를 덮는 것을 줄이기 위한 처리다. 현재 실행 ID가 바뀌면 다음 조회의 새 상태와 이벤트로 교체한다.

상태와 이벤트는 원자적으로 읽는 하나의 API가 아니다. 두 요청 사이에 완료·서버 재시작이 일어날 수 있으므로 같은 run_id이며 snapshot.last_event_sequence 이하인 이벤트만 표시한다. 새 이벤트는 다음 조회에 나타날 수 있다. 서버 측 원자적 읽기를 구현했다고 설명하지 않는다.

요청이 실패하면 이전 수치와 이벤트를 지우고 수신 대기·—·오류를 표시한다. 기존 정적 설비 정의는 모델 미리보기로 유지하지만 가짜 실시간 수치는 만들지 않는다. 시작 POST는 같은 요청을 자동 재시도하지 않고, READY일 때만 버튼을 활성화한다. 서버의 409 거절 규칙도 그대로 유지한다.

### 서버에서 장면까지의 흐름

```text
HTTP 상태 수신 → useFactoryConnection
  → FactoryDashboard의 현재 stationStates
  → FactoryViewport → FactoryScene → StationModel
```

진행률은 `1 - 남은 시간 / 설정 처리시간`에서 계산한다. 장면이 독립적인 생산 타이머를 만들지 않는다. current_part_id가 없거나 서버 연결이 끊겨 상태가 지워지면 소재를 표시하지 않는다. 서버 연결 전에는 설비 배치와 형상 참고만 보여준다.

frameloop="demand"는 상태나 카메라 변화에 맞춰 렌더링하도록 하는 설정이다. 이번에는 매 프레임 생산 상태를 계산할 필요가 없어 선택했다. 실제 GPU 성능·프레임 수·최적화 효과는 측정하지 않았다.

## 16단계. 사용자 화면 보고로 Canvas 크기 문제 수정하기

### 이전 상태와 수정이 필요한 이유

15단계에서 기본 3D와 fallback을 작성했고 사용자 확인을 기다렸다. 사용자가 실제 화면을 첨부해 3D가 위쪽에 몰리고 잘린다고 보고했다. 이미지에는 영역 아래쪽의 큰 빈 공간과 상단에 잘린 설비가 보였다. 전체 3D나 생산 기능이 정상 확인됐다는 보고로 해석하지 않는다.

### 실제 변경과 원인 분석

scene.module.css의 `.canvasContainer:has(.layout)` 규칙은 2D fallback이 표시될 때 높이를 늘리려는 코드였다. 하지만 설치된 Fiber Canvas 소스를 읽으면 fallback이 WebGL 표시 중에도 canvas 태그의 대체 자식으로 DOM에 남는다. CSS :has는 화면에 실제 보이는지를 판단하지 않고 자손의 존재를 판단하므로 정상 3D에서도 조건이 맞는다.

그 결과 부모의 확정 높이를 auto로 바꾸고 자식의 height:100% 계산을 불안정하게 만드는 규칙이었다. 이를 제거하고 FactoryScene.tsx의 Canvas wrapper에 position:absolute·inset:0을 지정했다. 부모는 기존 clamp 높이와 position:relative를 유지한다. 카메라나 생산 규칙을 바꾸는 대신 표시 영역의 크기 관계를 수정했다.

### 새 개념과 코드 읽기

CSS 선택자는 DOM 구조를 기준으로 작동하며 “fallback이 현재 활성화됐는가” 같은 앱 상태를 자동으로 알지 못한다. 퍼센트 높이는 부모의 확정 높이에 의존하므로 부모 높이가 auto로 바뀌면 예상과 다른 크기가 될 수 있다. absolute/inset:0은 여기서는 높이가 정해진 relative 부모를 기준으로 Canvas wrapper를 배치한다.

FactoryViewport.tsx의 canvasContainer → scene.module.css의 높이 → FactoryScene.tsx의 Canvas style 순서로 읽는다. 설치된 `frontend/node_modules/@react-three/fiber/dist/react-three-fiber.esm.js`는 원인 분석용으로 읽었으며 수정하지 않았다. 직접 실행·크기 측정으로 재현한 것은 아니다.

### 이전 상태와 이번 작업의 이유

기본 3D에서는 공통 작업대와 유사한 기둥·헤드를 반복했다. 사용자는 공정들이 모두 비슷해 보이고 실제 공정 모델 같지 않다고 지적했다. 코드 도형을 개선하는 A와 Blender 자산을 제작하는 B를 제시했고 사용자가 A를 선택했다. 이번 작업은 그 선택에 따른 외형 개선이며 새로운 제작 도구나 실제 공법 도입은 아니다.

## 18단계. 차체 1개의 가공·이동·검사·적재 연결하기

### 이전 상태와 이번 작업의 이유

이전에는 ST-01에서 소재 1개를 처리하고 PAUSED/BLOCKED에 보관했다. 사용자가 현재 화면 정상 동작을 보고하고 다음 개발을 요청했다. 이동 시간은 기존 문서에서 제안이었으므로 1초/0초 선택지를 먼저 제시했고 사용자가 구간당 1초를 선택했다.

이번에는 같은 부품 ID를 5개 공정에 연결한다. 처리 22초와 이동 4초를 합쳐 총 26초다. 소재 20개 중 1개만 소비하고 완료한다. 20개 연속 생산·대기열 경합·고장·사용자 일시정지/재개/초기화는 아직 구현하지 않는다.

### 실제 변경과 이전 설계와의 차이

단독 엔진은 처음과 끝의 상태만 필요했지만 이제 부품이 어떤 형상·품질·위치인지 별도로 표현해야 한다. PartSnapshot은 ID·stage·phase·quality·설비/보관 위치를, TransferSnapshot은 출발·도착·시작 시각·기간·진행률을 담는다. 설비의 reserved_part_ids는 이동 전에 확보한 입력 자리를 나타낸다.

기존 single_station.py와 시작 API는 유지하고 single_part.py에서 같은 기반을 확장했다. runner는 READY일 때 요청 시나리오에 맞는 엔진을 선택하며 기존 run_id를 유지한다. 새 화면은 `/single-part/start`를 호출하고 이전 `/single-station/start`도 직접 사용할 수 있다. 이미 시작한 같은 실행에서 다른 시나리오로 바꿔 시작할 수는 없다.

응답에 part·transfer·scenario·도착 예약과 COMPLETED를 추가해 schema_version을 2로 바꿨다. 이동 규칙을 반영한 모델은 chassis-line-v2다. COMPLETED는 소재 20개 전체가 아니라 이번 차체 1개 시나리오의 완료를 뜻한다.

### 코드 읽기와 데이터 흐름

1. domain/models.py의 PartSnapshot·TransferSnapshot·FactorySnapshot과 enums.py를 읽는다.
2. api/routes/factory.py의 새 시작 경로 → simulation/runner.py의 엔진 선택을 읽는다.
3. simulation/single_part.py의 `_process_material()`에서 5개 공정 loop·timeout·이동 예약·품질 공개·적재를 읽는다.
4. `_step_through()`와 `advance_to()`에서 목표 시각까지 이벤트를 처리하고 현재 처리/이동 진행을 스냅샷으로 표현하는 흐름을 읽는다.
5. 프론트 API → useFactoryConnection → 대시보드 → PartDetails·FactoryScene → partPosition·PartModel 순서로 읽는다.

```text
시작 POST + run_id → 단일 차체 엔진
  → 소재 1개 소비·부품 ID 생성
  → 공정 처리 → 형상 단계 갱신
  → 다음 입력 자리 예약 → 1초 이동 → 도착·예약 해제
  → 검사 완료 시 품질 공개
  → 적재 완료 시 수량 반영·COMPLETED

상태 GET의 part·transfer
  → 차체 추적 패널·서버 위치 기반 3D 부품 1개
```

### 새 개념: 단계와 위치를 분리하기

stage는 RAW→FRAME→DRILLED라는 형상 단계이고 phase는 PROCESSING/TRANSFERRING/STORED라는 진행 단계다. 프레임인 채로 이동할 수 있고 구멍 가공 차체가 검사 중일 수도 있어 서로 다른 정보로 관리한다.

이동할 때 출발 설비의 current_part_id를 비우고 도착 설비에 reserved_part_ids를 기록한다. 실제 부품은 transfer에 있다. 도착하면 예약을 해제하고 다음 설비에서 같은 ID를 처리한다. 예약한 부품을 입력 대기로 세면 아직 이동 중인데 waiting_count가 늘어나므로 이번에는 예약과 실제 대기를 구분했다. 한 부품만 있어 대기열 포화나 여러 작업의 경쟁까지 해결한 것은 아니다.

### 검사·수량·이벤트

실행 시작 때 고정 시드의 Random으로 결과를 한 번 정하고 검사 완료까지 UNINSPECTED만 공개한다. 품질은 모델 규칙이며 LLM이나 카메라 AI가 판정하지 않는다. 검사 외형과 실제 비전 인식 구현을 구분한다.

검사에서 양품이 나와도 양품 생산량을 바로 올리지 않는다. 적재가 끝날 때 라인 내부 1을 0으로 바꾸고 양품/불량 보관 수량을 올린다. 소재 19+라인 내부 1=20에서 소재 19+보관 1=20으로 바뀐다.

공정 시작·완료 10개, 이동 시작·도착 8개, 품질 공개·보관·시나리오 완료 각 1개로 이벤트 21개를 기록한다. 모두 같은 run_id·part_id를 사용한다. state_version은 진행 표시마다 갱신되므로 이벤트 sequence와 같을 필요가 없다.

### 3D 형상 변화와 보간

PartModel은 RAW일 때 소재 상자, FRAME일 때 레일 두 줄·가로 연결부 세 개, DRILLED일 때 레일에 구멍이 있는 형상으로 표시한다. Three.js Shape의 holes로 2D 윤곽에 구멍을 정의하고 ExtrudeGeometry로 레일 두께를 만든다. 구멍 윤곽은 바깥 윤곽과 반대 방향으로 구성한다. [Shape](https://threejs.org/docs/pages/Shape.html), [ExtrudeGeometry](https://threejs.org/docs/pages/ExtrudeGeometry.html)

레일 두께·구멍 크기·배치는 도식적 표현이며 미정인 제작 치수를 확정한 것이 아니다. 형상 변화는 서버가 공정 완료 시 stage를 바꿀 때 일어난다. 검사 완료 후에만 공개 품질에 따라 색을 바꾼다.

partPosition은 서버 transfer.progress로 설비 사이 좌표를 계산하고 ST-05 처리 진행률로 적재함 쪽 표시 좌표를 계산한다. PartModel의 프레임 보간은 최신 서버 목표 위치까지만 부드럽게 접근한다. 클라이언트가 시간을 앞서 진행하거나 완료를 결정하지 않는다. 실행 ID와 부품 ID를 key로 묶어 새 실행을 이전 부품 위치에서 이어서 표시하지 않는다.

실제 부품은 장면에서 한 번만 렌더링하고 전체 시나리오에서는 설비별 기존 소재 표시를 숨긴다. 별도의 참고 프레임은 여전히 `생산품 아님`으로 구분한다. 적재 위치 보간과 도구 움직임은 공정 설명용 표현이며 물리 시뮬레이션은 아니다.

### 새 개념: 두 시계와 명령의 경계

실제 시간은 일시정지 중에도 흐르지만 시뮬레이션 시간은 멈춰야 한다. 실행 중 목표 시각은 `재개 당시 시뮬레이션 시각 + 재개 후 실제 경과시간`이다. 예를 들어 시뮬레이션5초에서 실제10초를 쉬고 재개한 뒤1초가 흐르면 생산 시각은6초다. 멈춘 동안 SimPy timeout을 소비하지 않으므로 남은 가공·이동을 그대로 이어간다.

SimPy의 env.now는 마지막으로 처리한 이산 이벤트 시각이다. 가공 중 화면에 표시하는 시각은 그 사이에 있을 수 있다. 사용자 제어 이벤트에는 스냅샷의 시뮬레이션 시각을 사용해 정지 이벤트가 이전 공정 시작 시각으로 기록되지 않게 했다. 재개 이벤트는 같은 시뮬레이션 시각에 새 순번으로 기록된다.

제어 함수는 단일 asyncio 이벤트 루프에서 await 없이 실행 ID 확인·상태 변경·시계 갱신을 수행한다. 따라서 함수 중간에 다른 요청의 초기화가 끼어들지 않는다. 이전 타이머에는 자신이 시작한 엔진을 전달하고, 현재 엔진과 같을 때만 진행시켜 초기화 이후 새 실행을 오래된 시계로 움직이지 않게 한다. 다중 worker나 영속 DB까지 해결한 구조는 아니다.

일시정지 요청 직전 마지막 조회 이후에도 생산은 진행될 수 있다. 서버는 명령 시각까지 시간을 반영하고 아직 실행 중일 때만 멈춘다. 이미 완료됐다면409를 반환하고 완료 상태를 유지한다. 클라이언트는 재조회로 실제 결과를 받는다.

### 새 개념: FIFO·예약·역압과 수량 보존

FIFO는 먼저 도착한 부품을 먼저 꺼내는 규칙이다. Store는 도착한 부품을 보관하지만, 이동 중인 부품은 아직 Store에 없다. 따라서 Store 크기만 제한하면 동시에 출발한 부품들이 남은 자리를 중복으로 사용할 수 있다. Container 토큰을 출발 전에 확보해 이동 중에도 자리를 점유하도록 만들었다.

`queued_part_ids + reserved_part_ids`의 개수는 최대3이다. 현재 가공/출력 대기 부품은 그3개와 별도다. 예약 토큰은 도착할 때 반환하지 않는다. 도착 예약이 실제 입력 대기로 바뀌어도 같은 공간을 쓰므로 가공을 시작해 대기 공간을 떠날 때 반환한다.

**역압(backpressure)**은 뒤쪽 공간 부족 때문에 앞쪽 작업이 멈추는 현상이다. ST-02의8초 처리보다 ST-01의2초 투입이 빠르므로 ST-02 앞에 대기가 쌓인다. 공간이 차면 ST-01은 완료 차체를 들고 기다린다. OUTPUT_BLOCKED/OUTPUT_UNBLOCKED를 기록하지만 가공 완료를 두 번 기록하지 않는다.

수량은 `소재 잔여 + 투입 후 미적재 + 양품 + 불량 = 20`으로 보존한다. waiting_count는 미적재 부품의 일부다. 이 값을 다시 더하면 대기 부품을 두 번 센다. 부품 상태 목록에서 수량을 계산해 가공/이동/대기 전환 때 별도 수량 증감을 놓치는 문제를 줄였다.

여러 프로세스가 있다는 것은 여기서 CPU 스레드 병렬 실행을 뜻하지 않는다. SimPy가 같은 시뮬레이션 시각의 이벤트를 순서대로 처리하면서 공정들이 겹쳐 진행되는 모델이다. 기존 runner의 단일 시계만 진행시키므로 공장 일시정지는 모든 설비·이동을 함께 멈춘다.

### 이전 상태와 작업 이유

20단계까지1개/20개 생산과 공장 전체 정지·재개를 작성했다. 이 변경들은 사용자 확인 대기다. 사용자의 다음 작업 요청으로 기존 계획의 수동 설비 고장·복구를 연결했다. 고장은 특정 설비만 멈추고 다른 설비·이동·공장 시계는 계속 진행해야 하므로 공장 PAUSED를 재사용할 수 없다.

### 실제 변경과 전후 차이

- simulation/station_runtime.py에 설비별 가공 시간·고장 신호·복구 신호를 분리했다. 기존의 단일 timeout 대기를 `가공 완료 또는 고장 신호` 대기로 바꾸고, 고장일 때 남은 시간만 보관해 복구를 기다린다.
- single_station.py는 공통 fault/repair, 명령 시각 정렬, status_before_fault·FAULTED와 이벤트를 관리한다. 단독·1개·20개 엔진이 같은 중단 가공 로직을 사용한다.
- batch.py는 소재 투입 전, FIFO 꺼낸 직후, 가공 중, 출력 자리 확보 중에 고장 gate를 연결했다. 출력 대기 중 고장에는 공간 요청을 취소/반환하고 복구 후 다시 요청한다.
- single_part.py는 다음 설비가 고장 났으면 도착 부품을 QUEUED로 표시하고 복구 후 가공을 시작한다. 고장으로 완료가 늦어지므로 목표 시각의 기존2초/26초 상한을 제거하고 실제 완료 이벤트 시각에서 끝낸다.
- schema5에 설비의 고장 전 상태와 이벤트 part_id=null 허용을 추가했다. 부품이 없는 설비 고장에 가짜 부품 ID를 넣지 않는다. 고장 자체로 단계·품질·재고를 바꾸지 않는다.
- 설비별 POST fault/repair와 화면 버튼·고장 전 상태·차체 중단 표기·3D 고장 색/도구 위치 보존을 연결했다. 공장 정지 중 복구는 표시를 해제하지만 작업은 공장 재개까지 기다린다.

### 새 개념: 경쟁 이벤트와 남은 시간

SimPy의 `timeout | changed`는 완료 시간과 고장 신호 중 먼저 발생한 쪽을 기다린다. 가공 시작 시각과 고장 시각의 차이만큼 처리했다고 계산하고 남은 시간을 보관한다. 복구 후 새 timeout은 남은 시간만 기다린다. 완료 신호가 먼저라면 잔여시간을 정확히0으로 둬 부동소수점 오차 때문에 아주 작은 가공을 계속 예약하지 않게 한다.

이전 timeout 자체가 나중에 발생할 수 있어도 가공 완료는 해당 generator가 한 번만 수행한다. 고장 시에는 그 generator가 복구를 기다리므로 오래된 timeout만으로 PROCESS_COMPLETED가 기록되지 않는다. 가공 완료/품질 공개/적재는 공정 흐름 안에 남기고 고장 명령에서 실행하지 않는다.

출력 대기도 경쟁 이벤트다. `입력 자리 확보 | 고장 신호`를 기다리며 고장으로 깨어났다면 미완료 요청은 취소하고 이미 얻은 자리는 반환한다. 복구됐다는 이유만으로 자리 확보에 성공한 것으로 처리하면 안 된다. 실제 공간 요청이 완료됐는지도 함께 확인해야 한다. 이 조건은 공장 정지 중 고장·복구를 연속으로 실행했을 때도 중요하다.

### 명령 시각과 공장 일시정지

스냅샷 시각은 마지막 SimPy 이벤트 사이에 있을 수 있다. 가공 시작3초, 표시 시각5.4초에 고장을 명령하면 SimPy 명령 시각도5.4초로 맞춰2.4초만큼의 가공을 차감한다.3초 시점에서 고장 처리하면 잔여시간이 잘못 보존된다.

공장 일시정지는 시계를 고정한다. 그동안 설비 복구 이벤트는 등록할 수 있지만 worker를 깨워 FIFO를 옮기거나 새 소재를 투입하지 않는다. 공장 재개 때 같은 시각의 대기 신호를 처리한 후 시계를 진행한다. 공장 재개와 설비 복구는 각각의 상태를 해제하므로 둘 중 하나가 다른 하나를 자동으로 해제하지 않는다.

고장 전 PROCESSING·BLOCKED·IDLE를 보관해 복구 시 원래 맥락으로 돌아간다. 예를 들어 BLOCKED를 복구한 뒤 공간이 비었으면 출발하고 아직 가득 차면 계속 기다린다. 가공이 이미 완료된 부품을 다시 가공하지 않는다.

- persistence/models.py는 테이블을, repository.py는 트랜잭션 저장/조회를, writer.py는 실행별 대기 상태 병합·비동기 저장·재시도를 맡는다.
- runner.py에서 이벤트/명령 변화와 주기 상태를 전달하고, 초기화 전 실행과 정상 서버 종료 기록을 별도 이유로 보관한다. app.py lifespan에서 저장 작업자·DB 엔진의 수명을 관리한다.
- 이벤트에 UTC 실제 발생 시각 occurred_at을 추가했다. 공장 시각과 별개이며 schema6으로 표시한다.

**마이그레이션**은 DB 구조 변경을 순서 있는 파일로 남기는 방식이다. 서버 시작 때 테이블을 몰래 만들지 않고 사용자가 alembic upgrade head로 적용한다. **트랜잭션**은 마지막 실행 상태·부품·신규 이벤트를 함께 저장하거나 함께 취소하는 경계다. 실행에 마지막 이벤트 순번이21로 기록됐는데 이벤트 행은15개만 저장되는 중간 상태를 커밋하지 않도록 한다.

이벤트의 기본 키는 실행 ID와 순번의 조합이다. 같은 자료를 재전송해도 두 번 삽입하지 않는 **멱등성**을 제공한다. 부품 ID도 run_id와 함께 저장하며 상태 버전이 오래된 자료로 최신 상태를 덮지 않도록 한다. 시드·모델·설정은 스냅샷에 보존한다. 이것만으로 전체 명령 재현이나 엔진 복원이 완료된 것은 아니다.

### 생산 시계와 저장 대기

DB I/O를 가공 루프에서 기다리면 DB가 느려질 때 생산도 멈출 수 있다. 러너는 불변 스냅샷과 누적 이벤트를 비동기 작업자에게 전달한다. 같은 실행의 대기 상태는 최신 것으로 합치지만 이벤트는 누적 전체를 유지하고 다른 실행은 별도 키로 보관한다.

명령 응답 성공과 DB 커밋은 다른 시점이다. 저장 상태 API에서 활성 여부·대기 실행 수·최근 오류를 제공한다. DB 장애 때 재시도하지만 미저장 대기열은 메모리다. 강제 종료로 미커밋 기록이 유실될 수 있고 정상 종료도 최대5초만 기다린다. 영속 outbox·장애 중 무손실 처리는 아직 구현하지 않았다. 현재 단일 API worker 전제도 유지한다.

RESET·SERVER_STOP은 실행 보관 이유다. RUNNING 중 서버를 종료해도 생산을 COMPLETED로 위조하지 않는다. 강제 종료로 보관 표식이 없는 기록도 “마지막 저장 상태”로 읽어야 한다. 저장한 스냅샷을 읽는 것과 SimPy generator·자원 대기 상태를 되살리는 것은 다르다.

### 코드 읽기와 데이터 흐름

1. compose.yaml·backend/pyproject.toml·settings.py·migrations에서 DB와 스키마 준비 경계를 읽는다.
2. persistence/models.py → repository.py에서 run_id·이벤트 복합 키·JSONB 스냅샷·트랜잭션을 읽는다.

엔진 변화 → 불변 자료 전달 → 실행별 대기 → PostgreSQL 트랜잭션 → 대기 제거 순서다. 동시 생산 규칙은 도메인/엔진에 남고 DB 저장소가 가공 완료를 결정하지 않는다. 부품 없는 고장 이벤트의null과 단독 ST-01의 설비 내 부품도 보관한다.

**도구 계약**은 이름·허용 입력·반환 자료·오류의 약속이다. LLM이 나중에 호출하더라도 실행 ID·UUID·limit·대상을 검사하는 서버 경계를 통과해야 한다. 임의 SQL이나 생산 명령을 실행하는 통로를 만들지 않았다. 각 조회에는 expected_run_id를 넣어 초기화 직전의 질문을 새로운 실행에 조용히 적용하지 않도록 한다.

**관측 시점**은 조회 결과가 어떤 공장 상태를 읽었는지 뜻한다. 같은 이벤트 루프에서 await 없이 불변 스냅샷과 이벤트 튜플을 읽고, 이벤트는 그 실행과 마지막 순번까지 제한한다. run_id·state_version·last_event_sequence·시뮬레이션 시각·실제 조회 시각을 함께 돌려준다. 별개의 도구 호출 사이에는 생산이 진행되므로 서로 다른 상태 버전일 수 있다. 후속 분석은 이 차이를 고려해야 한다.

최근 이벤트는 일치한 자료의 마지막N개만 반환하고 순번은 오름차순으로 유지한다. matched_count와 truncated를 표시해 제한된 자료를 전체 이력처럼 해석하지 않게 한다. 부품 없는 고장 이벤트는 설비 조회에 포함되지만 특정 부품 이력에서는 제외된다. 단독 엔진의 부품 상태가 별도 모델로 없을 때 part=null을 반환하며 실제 ID·이벤트는 보존한다.

대기열 수·예약·빈 자리는 직접 계산한 사실이다. 이 숫자만 보고 “ST-02가 모든 지연의 원인”처럼 결론을 만들지는 않는다. 서버 메모리 관측과 DB 커밋, 현재 부품 이력과 과거 저장 실행도 구분한다.

**부분 사용량**은 이미 받은 응답에서 확인한 토큰만 합산한 값이다. 두 번째 요청이 통신 실패해도 첫 번째 응답의 사용량은 사라지면 안 된다. 그래프가 최종 답변을 반환할 때만 수치를 모으면 이 부분을 잃는다. 요청 직전 시도 수를 늘리고 수신 시점에 사용량을 모아 model_calls와 reported_calls를 비교한다. 미수신 요청의 사용량은0이라고 확정하지 않는다.

**결과 상태와 과금**도 다르다. 답변 형식 오류나 잘못된 인용으로 실패해도 모델은 이미 토큰을 사용했을 수 있다. incomplete 응답에 사용량이 있으면 실패 결과에도 보존한다. usage_complete=true는 시도한 요청들의 사용량을 모두 받았다는 뜻이며 실제 청구를 검증했다는 뜻이 아니다. 추정 비용과 최종 청구는 구분한다.

**비동기 저장의 완료 경계**는 답변 처리와 다르다. X-Analysis-History=queued는 저장 요청을 메모리에 넣었다는 뜻이다. DB 커밋은 저장 작업자가 나중에 수행한다. 접수 revision0이 저장 중일 때 종료 revision1이 들어와도 이전 저장 완료가 새 대기를 지우면 안 된다. 기존 생산 저장에서 배운 객체 동일성 비교와 DB revision 조건을 분석에도 적용했다.

생산 행과 분석 행은 서로 다른 작업자가 저장한다. 생산 실행의 커밋을 기다리지 않고 분석을 보관하기 위해 run_id를 관측 식별자로 두고 외래 키를 만들지 않았다. 같은 실행 UUID를 공유하지만 이 자료만으로 생산 엔진을 복원하지 않는다. 강제 종료로 RUNNING만 남으면 ‘완료 정보 없음’으로 읽으며 현재 분석 중이라고 추정하지 않는다.

### 실제 변경과 새 개념

- runner.py에 구독·해제와 최대 1프레임 큐를 추가했다. 기존 상태 포착 위치에서 DB 설정 여부와 관계없이 현재 불변 상태와 누적 이벤트를 발행한다. 연결 시에도 같은 형식의 초기 프레임을 큐에 넣는다.
- factory 라우트에 /api/factory/stream을 추가했다. 상태와 이벤트를 한 JSON으로 보내고 변경이 없을 때 5초 heartbeat를 보낸다. 송신과 연결 종료 수신을 별도 task로 기다리며 종료 시 task와 구독을 정리한다. WebSocket에서는 생산 명령을 실행하지 않는다.
- pyproject.toml에 websockets를 선언하고 Vite 프록시에 ws: true를 추가했다. 설치와 잠금 파일 갱신은 사용자가 수행한다.
- factoryStream.ts가 주소와 protocol_version=1 메시지 구분을 맡는다. useFactoryConnection은 HTTP 반복 조회 대신 소켓 수신, 낮은 상태 버전 제외, 끊김 안내, 수신 제한 시간과 재연결을 관리한다. 생산 제어 POST는 유지하고 HTTP 응답으로 화면 상태를 덮어쓰지 않는다.

**하나의 관측 프레임**은 상태와 이벤트를 같은 시점에 포착해 함께 보낸다는 뜻이다. 기존 두 조회 사이에 생산이나 초기화가 일어나는 간격을 줄이기 위해 전송 단위를 묶었다. 별도의 await 없이 상태와 불변 tuple을 읽으며 이벤트를 실행 ID와 마지막 순번에 맞춘다. 다른 서버 프로세스까지 하나의 관측으로 만드는 기능은 아니다.

**최신 프레임 병합**은 느린 연결을 위해 모든 중간 상태를 큐에 쌓지 않는 방식이다. 대기 중인 한 프레임을 최신 것으로 교체한다. 각 프레임에는 누적 이벤트가 있어 다음 수신으로 이력을 회복할 수 있다. 이벤트를 증분으로만 보냈다면 버린 프레임의 이벤트를 별도로 재요청해야 한다. 현재 20개 생산에서는 단순한 누적 전송을 택했지만 무한 생산에는 전송량과 보관 범위를 다시 설계해야 한다.

**연결 수명과 상태의 권위**도 구분한다. 소켓 open만으로 유효 상태 수신을 확정하지 않고 첫 상태를 받은 뒤 연결됨으로 표시한다. 끊기면 제어를 막고 재접속 시 전체 상태를 다시 받는다. 제어 POST가 처리되는 동안 더 최신 상태가 소켓으로 올 수 있으므로 늦은 HTTP 응답이 화면을 이전 버전으로 되돌리지 않게 한다. 전송 실패한 명령을 자동 재전송하면 중복 제어 가능성이 있어 조회 연결만 재시도한다.

## 28단계. 실행 ID와 방문자 소유권을 구분하기

### 앞 단계의 상태와 이번 작업이 필요한 이유

27단계까지 WebSocket 상태/이벤트 수신과 자동 재연결을 작성했지만 서버는 공장 하나를 모든 화면에 공유했다. 따라서 다른 방문자의 초기화가 내 생산을 지울 수 있었다. 첫 공개 준비에서 공유 유지와 방문자별 분리를 제시했고 사용자가 분리를 선택했다. 이전 기능의 설치/DB/실제 호출 결과는 여전히 확인 대기다. 추가 횟수·지출·접근 제한을 원하지 않는다는 결정도 유지한다.

### 실제 변경

- api/visitors.py에 익명 Visitor·VisitorRegistry를 추가하고 app lifespan에서 하나의 runner 대신 registry 수명을 관리한다. 각 방문자가 처음 접근할 때 독립 runner를 생성하고 종료 시 모두 정리한다.
- POST /api/session은 임의 토큰의 HttpOnly·SameSite=Lax 쿠키를 준비한다. 쿠키를 가진 HTTP/WS가 공통 VisitorDependency로 자기 runner를 선택한다. 실행 ID 검사는 그 runner 안에서 수행한다.
- 원문 토큰 대신 SHA-256 지문 owner_id를 저장 대기에 전달한다. 세 번째 migration으로 생산/분석 이력에 owner_id·인덱스를 추가하고 목록·상세·부품/이벤트 조회에 소유자 조건을 둔다. 기존 소유자 미상 기록은 NULL로 보존하며 임의로 배정하지 않는다.
- frontend/api/session.ts의 준비 Promise와 쿠키 기반 visitorFetch를 모든 기능에 연결했다. 지원 환경의 Web Locks로 여러 탭의 최초 준비를 직렬화한다. 소켓도 준비 후 열고 재접속 전에 다시 준비한다. 화면에 내 공장·내 이력 범위를 표시한다.
- 기존 서버 공통 분석 잠금/호출 간격·요청별 보호 장치는 유지한다. 새 횟수/지출 제한이나 유휴 종료를 임의로 도입하지 않았다.

### 새 개념: 실행 식별과 소유권은 다른 질문이다

run_id는 “내가 보고 있는 생산 실행이 아직 같은가?”를 판단한다. 초기화 전 ID로 다시 명령을 보내는 실수를 막지만, 공개된 ID를 알고 있는 다른 방문자를 구분하지는 못한다. 방문자의 쿠키로 runner를 먼저 선택하고 그 안에서 expected_run_id를 검사해야 서로의 생산에 접근하지 않는다. 이력 조회에도 소유자 조건을 적용해야 한다. 프론트엔드에서 목록만 숨기면 상세 URL로 접근하는 경로가 남는다.

익명 쿠키는 계정 로그인이 아니라 소유권을 가진 브라우저를 다시 알아보는 자격 정보다. 256비트 임의 토큰을 발급하고 원문은 HttpOnly 쿠키에 둔다. 서버 registry와 DB에는 단방향 지문만 사용한다. 지문을 안다고 원문 쿠키가 되는 것은 아니지만, 원문 쿠키가 유출되면 그 브라우저 소유권을 사용할 수 있으므로 URL/로그/문서에 넣지 않는다. SameSite와 Origin 검사는 다른 사이트의 브라우저 요청 경계를 다루며 방문 횟수 제한과 다르다. HTTPS에서는 Secure 설정이 필요하다.

공장은 브라우저 탭마다 분리하지 않는다. 같은 쿠키를 쓰는 탭은 같은 방문자로 취급한다. 탭을 각각 다른 사람으로 만들면 새로고침·이력·다중 탭의 의미가 달라진다. 첫 준비를 여러 탭에서 동시에 실행할 때 서로 다른 쿠키를 발급받지 않도록 가능한 환경에서 Web Locks를 사용한다. 페이지 내부 Promise 공유와 여러 탭의 직렬화는 서로 다른 범위다.

DB migration은 새 필드가 기존 데이터에 어떤 의미인지도 결정한다. 기존 공유 기록에는 방문자 소유자가 없으므로 현재 사용자에게 자동 배정하면 안 된다. nullable 필드로 원본 기록을 보존하고 새 방문자 조회에서 제외한다. 서버 재시작 시 쿠키 지문은 같아 과거 이력은 찾지만 실행 엔진 자체는 새로 생성된다. 이력 소유권의 지속과 SimPy 실행 복원은 별개다.

### 실제 변경과 새 개념

- Visitor에 last_activity와 active_requests를 추가했다. monotonic 시계로 실제 경과 시간을 기록한다. 시뮬레이션을 일시정지해도 유휴 경과 시간은 흐른다.
- 공통 방문자 의존성을 return에서 yield로 바꿨다. 주입부터 HTTP 응답/WS 종료까지 사용 중 카운트를 유지하고 finally에서 감소·활동 시각을 갱신한다. 오류나 취소도 정리 경로를 따른다.
- registry에30초 정리 루프를 두었다. 사용 중인 수가0이고 마지막 활동이1800초 이상인 방문자의 엔진만 분리한다. 마지막 탭 종료와 처리 중 분석을 같은 수명 보호 경계로 다룬다.
- 분리한 runner는 별도 task에서 종료하고 IDLE_EXPIRED로 기존 이력 저장 큐에 제출한다. 앱 종료 시 정리 루프를 멈추고 진행 중인 엔진 종료도 기다린다. 새 방문자가 이전 엔진 종료 도중 돌아와도 새 run_id의 엔진을 받는다.
- settings/.env.example의 기본1800초 설정과 생산 이력의 유휴 종료 사유 표시를 추가했다. 새 DB migration/패키지는 없다.

**사용 중이라는 증거**는 브라우저를 닫았다는 추측보다 명확해야 한다. 탭 하나가 닫혀도 다른 탭의 WebSocket이 살아 있으면 같은 방문자는 사용 중이다. 분석 HTTP 요청 중에도 엔진이 사라지면 안 된다. yield 의존성은 공통 입구와 종료 지점이 있어 이 수명 카운트를 한곳에서 관리할 수 있다. 활동 시각만 최초 접근 때 기록하면 오래 열린 연결까지 유휴로 잘못 판단한다.

**마지막 활동 시각과 검사 주기**는 서로 다르다. 기준은30분이지만 검사 주기가30초이므로 정리는 기준을 넘은 다음 검사에서 일어난다. 로컬 확인에서15초로 바꿔도15초 정확히 정리된다고 기대하면 안 된다. monotonic은 시스템 벽시계 보정에 영향을 덜 받는 경과 시간용 시계이며, DB의 실제 UTC 발생 시각을 대체하지 않는다.

**엔진 분리와 종료의 순서**도 중요하다. 후보 확인과 registry 삭제 사이에는 await를 두지 않는다. 삭제 뒤에는 새 방문자가 새 엔진을 만들 수 있다. 예전 엔진의 task 취소/이력 제출이 새 엔진을 다시 지우면 안 되므로 이전 객체를 종료하고 새 객체를 registry에서 건드리지 않는다. 종료 작업은 추적해 서버 종료와 경합해도 기다린다.

**실행 종료와 이력 보존**은 다르다. 유휴 정리는 라이브 엔진의 메모리를 회수한다. DB 기록은 삭제하지 않고 소유자 쿠키도 바꾸지 않는다. 저장 당시 run_status가 RUNNING이어도 closed_reason=IDLE_EXPIRED이면 유휴 종료로 읽어야 한다. 정상 COMPLETED로 바꿔 미완료 생산을 성공으로 표현하지 않는다. 저장 큐 제출이 DB 커밋이라는 뜻도 아니다.

- useGuidedTour는 생산·고장·분석·복구의 진행을 서버 상태와 응답 버전으로 판단한다. 사용자가 직접 분석을 요청하며 실패했을 때 성공 단계를 꾸며 진행하지 않는다.

### 새 개념

**공간 탐색 상태와 생산 상태의 분리:** 카메라가 조립 전시 구역으로 이동해도 생산 엔진이 조립을 실행하는 것은 아니다. SpatialFocus는 보고 있는 위치이고 FactoryState는 서버가 계산한 사실이다. 이를 섞으면 화면을 떠났다는 이유로 생산을 멈추거나 전시 모형을 실제 생산품으로 오해하게 된다.

**필요할 때 정보를 공개하는 화면:** 기존 상세와 이력을 삭제하지 않고 사용자의 선택 뒤에 배치한다. 첫 화면에서는 생산을 이해하고, 선택하면 설비를 이해하고, 근거를 펼치면 데이터를 읽는다. 기능 수를 늘리지 않아도 정보를 만나는 순서를 바꿔 제품 경험을 바꿀 수 있다.

**카메라 보간과 시뮬레이션 시간:** 카메라는 목표 위치와 확대값으로 부드럽게 접근한다. 부품 표현도 서버 위치로 접근하지만 그 보간이 생산 결과를 결정하지 않는다. 렌더링이 느리거나 정보창을 열어도 서버의 가공 시간과 완료 수량은 별개다. 감소된 모션과 수동 카메라 조작을 별도로 처리한다.

**관측 기반 AI 시각화:** 답변의 관련 설비 강조는 모델이 참조한 대상의 표시다. 현재 고장 상태와 같은 의미가 아니므로 색과 관측 시각을 구분한다. 답변에 없는 영향 경로나 도구 진행 상태를 그럴듯하게 추가하지 않는다. 실제 이벤트 근거를 펼쳐 읽을 수 있지만 근거 존재와 설명의 정확성은 별도 사용자 확인 대상이다.

**컴포넌트 수명과 요청 수명:** 닫힌 정보창은 숨겨지지만 상위 질문 훅은 유지된다. 따라서 닫았다 열어도 답변이 남는다. 실행 ID가 바뀌면 keyed SimulationExperience를 새로 만들고 기존 훅은 abort 정리를 한다. 브라우저 요청을 취소한다고 이미 공급자에 전달된 요청 비용까지 취소되는 것은 아니다.

**안내 단계의 상태 기계:** 다음 버튼을 누른 횟수로 체험 성공을 판정하면 실패 요청도 성공처럼 보인다. reducer는 생산 RUNNING, ST-02 FAULTED, 고장 관측 버전 이후의 실제 분석 응답, 복구된 서버 상태를 각각 사용한다. 이는 앱 안내 진행일 뿐 사용자가 이해하거나 검증을 완료했다는 기록은 아니다.

### 실제 변경

- 공식 Blender4.5.3 포터블을 프로젝트 외부 도구 폴더에 준비하고 Python 제작 스크립트를 백그라운드에서 실행했다. 편집용 forming-cell.blend와 웹용 forming-cell.glb를 생성했다. 원본 파일 제작은 수행했지만 화면 품질 검증은 하지 않았다.
- ST-02의 외장 모서리, 분할 패널, 테이블/T슬롯, 레벨링 풋, 레일·스핀들·지그, 측면 안전창, 제어판, 배선·환기 구조와 재질을 작성했다. 생산품은 모델에 넣지 않고 기존 서버 부품 표현을 사용한다.
- 편집 원본은 개별 부품을 유지하고 웹용 내보내기에서만 재질/가동 부모별로 메시를 합쳤다. CarriageX·SpindleSlide·ClampFront·ClampBack 이름을 가동 계약으로 정했다.
- FormingCellAsset이 useGLTF로 로드하고 기존 StationModel/ProcessEquipment에 연결한다. 모델에 포함된 테이블/상태등과 기존 공통 모형의 중복 표시를 제외했다. 실패하면 해당 모델만 기존 도형으로 대체한다.
- formingCellMotion이 서버 진행률을 고정·접근·가로 가공·상승·해제의 시각 동작으로 변환한다. 기존 가공 중 고장 포즈를 유지하며 자체 시계로 생산을 진행하지 않는다.
- FactoryLighting에 직접 조명과 로컬 생성 반사 환경을 추가했다. 조명 색은 공통 토큰으로 관리한다. 새 원격 HDR/텍스처나 npm 패키지는 추가하지 않았다.

### 새 개념

**편집 자산과 배포 자산:** Blender 원본에는 수정하기 쉬운 개별 부품을 남기고, GLB에는 브라우저가 표시할 메시·재질·계층을 담는다. 생성 스크립트는 제작 과정을 다시 실행할 수 있게 하지만 원본을 직접 수정한 뒤 재실행하면 덮어쓰므로 별도 편집본을 남겨야 한다. 파일 생성 성공과 실제 화면 완성도는 다른 상태다.

**모서리와 재질의 역할:** bevel은 날카로운 모서리에 작은 면을 만들어 빛을 받게 한다. weighted normals는 넓은 면의 음영을 정돈한다. 도장·가공 금속·고무·안전창은 색뿐 아니라 금속성·거칠기·투명도로 구분한다. 조명과 반사 환경이 없으면 이러한 차이가 충분히 드러나지 않을 수 있으므로 함께 설계했다. 실제 결과는 사용자 확인 대상이다.

**좌표계와 가동 계층:** 앱은 Y-up, Blender는 Z-up이다. 제작 스크립트에서 앱 좌표를 Blender 좌표로 바꾸고 glTF Y-up으로 내보낸다. 수치 스케일은1로 유지해 기존 소재 바닥 y=0.91와 연결한다. 스핀들은 캐리지의 자식이므로 가로 이동을 따라가면서 자체 Y축 하강도 할 수 있다. 노드 이름을 바꾸면 연결 계약도 함께 바꿔야 한다.

**프레젠테이션 동작과 엔진 공정:** 고정0–12%, 접근12–24%, 가공24–76%, 상승76–90%, 해제90–100%는 화면 연출 구간이다. 백엔드의8초 공정을 새로운 다섯 공정으로 바꾼 것이 아니다. 수신 진행률에서 포즈를 계산하므로 일시정지 때 멈추고, 가공 중 고장에는 status_before_fault와 remaining_process_seconds로 같은 맥락을 유지한다. 실제 절삭·충돌·정밀 안전 동작을 시뮬레이션하지 않는다.

**웹 자산의 공유와 복제:** useGLTF는 모델을 캐시한다. 원본 장면과 재질을 직접 바꾸면 재사용한 다른 인스턴스에 상태등/포즈가 섞일 수 있다. 장면과 재질을 복제하고 가동 노드만 수정한다. 정리할 때는 복제 재질만 해제하고 공유 지오메트리는 유지한다.

**부품 수와 렌더링 작업:** 볼트마다 별도 메시를 유지하면 표현 비용이 늘어난다. 웹용에서는 같은 가동 부모와 재질을 공유하는 부품을 합친다. 움직여야 하는 지그와 공구를 고정 외장과 합치면 제어가 어려워지므로 경계를 유지한다. 이번 작업에서 실제 FPS나 로드 시간을 측정한 것은 아니다.

### 실제 변경·개념·코드 흐름

SimulationExperience의 초기 소개 영역을 제거하고 tour.step이 off가 아닐 때만 진행 안내를 표시한다. 소개 메뉴의 기존 체험 진입은 유지한다. FactoryEnvironment의 Html과 scene.module.css의 campusMarker에 내용 기준 너비를 지정했다. max-content는 텍스트의 필요한 가로 너비를 유지하고 white-space:nowrap은 자동 줄바꿈을 막는다. 번호·이름은 grid 두 열, 부가 설명은 두 열을 가로지르는 별도 행이다. 모바일 번호만 표시하는 상태에서는 한 열로 배치한다.

읽기 순서: SimulationExperience의 tour.step 조건 → FactoryEnvironment의 Html/버튼 → campusMarker의 너비·줄바꿈·grid와 모바일 규칙. 3D 좌표에 놓인 HTML도 일반 CSS 레이아웃의 영향을 받는다는 점을 이해한다.

### 사용자 확인과 다음 단계

초기 소개 패널이 없어지고 구역 이름이 가로 한 줄로 보이는지, hover/선택 시 설명이 별도 행인지 직접 확인한다. 모바일 번호 표지와 구역 이동, 소개 메뉴의 체험 시작도 확인한다. 코드 작성 완료·사용자 확인 대기. 테스트·빌드·실행 검증은 수행하지 않았다.

직접 설명할 질문: 최대 너비만 지정했을 때와 내용 기준 너비를 지정했을 때 어떤 차이가 있는가? 한글의 자동 줄바꿈은 이름표에 어떤 영향을 주는가? 다음은 사용자의 실제 화면 피드백을 반영한다.

## 42단계 — 선택과 확대 배율을 분리하고 첫 시점으로 초기화하기

### 이전 상태와 이번 변경 이유

40단계에서 마우스 이동/회전을 연결했으나 선택 시 근접 배율이 적용되고 복귀는 선택 대상을 향했다. 기존 구현의 사용자 확인 대기는 유지한다. 사용자는 자동 확대를 없애고 초기화 버튼으로 첫 공장 시점에 돌아가도록 요청했다.

### 실제 변경·새 개념·코드 읽기

useSceneNavigation의 navigate는 선택만 변경하고 resetCamera는 overview와 초기화 카운터를 함께 변경한다. SimulationHud에서 ‘시점 초기화’를 호출한다. SpatialCamera는 이전 초기화 카운터와 현재 요청을 비교해 일반 탐색과 초기화를 구분한다. 일반 탐색에서는 camera.zoom과 camera.position에서 controls.target을 뺀 오프셋을 저장한다. 따라서 중심을 옮겨도 배율과 바라보는 각도는 유지된다. 초기화는 첫 진입과 같은 전체 보기 배율 계산 및 오프셋을 사용한다. useFrame은 이 목표까지 보간하며 수동 조작은 기존처럼 자동 이동을 중단한다.

읽기 순서: SimulationHud 버튼 → useSceneNavigation의 focus/resetView → FactoryScene의 overview 중심 좌표 → SpatialCamera의 framing과 useFrame. 선택 상태, 바라보는 중심, 확대 배율은 서로 다른 책임이라는 점이 핵심이다. 차체 위치 갱신은 중심 추적에만 사용하고 배율을 다시 결정하지 않는다.

### 사용자 확인·설명할 질문·다음 단계

휠로 크기와 우드래그로 각도를 바꾼 뒤 설비·차체·구역을 선택한다. 배율/각도는 유지되고 대상 중심 이동·차체 추적은 유지되어야 한다. 이동·회전·확대 및 차체 추적 중 초기화를 누르면 첫 접속의 전체 공장 시점으로 돌아와야 한다. 반복 초기화도 직접 확인한다. 코드·문서 작성 완료, 사용자 확인 대기이며 테스트·빌드·린트·실행 검증은 수행하지 않았다.
