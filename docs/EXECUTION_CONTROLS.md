# 일시정지·재개·실행 초기화

작성일: 2026-10-10 (Asia/Seoul)  
상태: 코드·문서 작성 완료, 사용자 확인 대기. 테스트·빌드·린트·서버 실행·HTTP 요청·브라우저 검증은 수행하지 않았다.

현재 schema5에 [설비 고장·복구](C:/project/truckworks/docs/STATION_FAULTS.md)를 추가했다. 공장 재개는 설비 고장을 해제하지 않는다. 공장 정지 중 설비를 복구해도 작업·FIFO·소재 소비는 공장 재개까지 기다린다. 기존 schema 메모는 당시 기록이다.

2026-10-10 후속: [20개 연속 생산](C:/project/truckworks/docs/BATCH_PRODUCTION.md)을 추가했다. 현재 schema4이며 제어는 여러 부품의 가공·이동·대기를 포함한 전체 실행에 적용한다. 아래26초·21개 이벤트 기대값은1개 시나리오를 선택했을 때의 기준이다.

## 사용 방법과 기대 결과

새 의존성은 없다. 백엔드를 재시작하고 프론트엔드를 새로고침한다. 전체 공정 시간표는 [SINGLE_PART.md](C:/project/truckworks/docs/SINGLE_PART.md)를 따른다.

1. 차체 1개 생산을 시작하고 ST-02 가공 중 일시정지를 누른다. 실행 상태는 일시정지, can_resume은 true여야 한다. 시뮬레이션 시간·남은 가공 시간·소재/수량·부품 ID가 몇 초를 기다려도 유지돼야 한다. 설비의 PROCESSING은 멈춘 작업을 보관하는 상태이며 전체 실행 상태가 PAUSED다.
2. 재개를 누른다. 같은 run_id·part_id와 남은 시간부터 이어져야 한다. 멈춰 있던 실제 시간은 생산 시간에 포함되지 않는다. 여러 번 멈춰도 최종 시뮬레이션 시간은 26초다.
3. 가능하면 시간표의 2–3·11–12·18–19·23–24초 중 이동 구간에서도 일시정지한다. transfer.progress·예약된 부품 ID가 유지되고 재개 후 같은 목적지로 나머지 이동을 마쳐야 한다. 짧은 구간이므로 아래 API로도 확인할 수 있다.
4. 실행 중·일시정지 중·완료 후 각각 초기화한다. 새로운 run_id, READY, 시각0, 소재20, 모든 생산 수량0, 모든 설비IDLE, 부품/이동null, 예약/이벤트없음, can_resume=false가 기대 결과다. 이후 서버를 재시작하지 않고 생산을 다시 시작할 수 있어야 한다.
5. 초기화 전 run_id를 보관해 새 실행에 제어 명령을 보내면 409여야 한다. 새 실행의 소재·이벤트·부품은 변하면 안 된다. 초기화 직후 다시 시작해도 이전 실행의 타이머·이벤트가 섞이지 않아야 한다.
6. 일시정지/재개 한 쌍마다 RUN_PAUSED·RUN_RESUMED 이벤트가 각1개 추가된다. 두 이벤트의 시뮬레이션 시각은 같고 순번은 증가해야 한다. 제어하지 않은 전체 공정은 기존21개, 한 쌍을 추가하면23개가 기대 결과다. 초기화하면 이전 이벤트는 지워진다.
7. 새로고침·다른 탭에서도 서버의 PAUSED와 재개 가능 상태가 유지돼야 한다. 요청 중에는 모든 제어 버튼이 잠시 비활성화된다. 실패/시간 초과 시 명령을 자동 재전송하지 않고 상태 조회를 재개한다.

3D는 새 정지 스냅샷의 위치까지 짧게 보간한 뒤 멈춘다. 정지 요청과 화면 반영 사이에는 HTTP/조회 지연이 있다. 부품 상세는 가공/이동 일시정지를 표시한다. 카메라 회전·설비 선택은 계속 가능하다.

## API로 확인할 항목

API 문서 `http://127.0.0.1:8010/docs`에서 현재 상태를 조회하고 아래 POST 모두에 같은 형태의 본문을 보낸다.

```json
{"expected_run_id":"현재 GET /api/factory/state의 run_id"}
```

| 경로 | 허용 상태 | 기대 응답 |
|---|---|---|
| /api/factory/pause | RUNNING | PAUSED, can_resume=true |
| /api/factory/resume | PAUSED이면서 can_resume=true | RUNNING, can_resume=false |
| /api/factory/reset | 현재 실행의 모든 상태 | 새 run_id의 READY |

잘못된 상태·이전 실행 ID는409, 잘못된 UUID·추가 본문 필드는422다. 연속 일시정지, 연속 재개, READY/COMPLETED에서 재개는 거절돼야 한다. 완료와 일시정지가 맞물리면 서버가 명령 시각까지 진행한 뒤 완료 상태를 우선하고 일시정지 요청은409로 거절한다. 현재 상태를 다시 조회하면 된다.

기존 `/single-station/start`의 2초 종료는 다음 공정 미연결로 PAUSED·can_resume=false다. 이 종료 상태에서 재개는409이며 초기화는 가능해야 한다. 처리 중 사용자가 일시정지한 경우만 남은 ST-01 가공을 재개할 수 있다.

## 구현 범위와 다음 작업

schema_version은3이며 재개 가능 여부를 can_resume으로 명시한다. 재개 때 실제 시간 기준점을 현재 시뮬레이션 시각에 다시 맞춘다. 제어 명령은 단일 이벤트 루프에서 await 없이 ID 확인·상태 변경을 수행한다. 이전 타이머는 초기화 때 취소하고 엔진 동일성도 확인한다. 이 구조는 기존 단일 worker·메모리 상태 전제이며 DB 저장·여러 서버 간 제어를 제공하지 않는다.

초기화는 현재 생산·이벤트를 폐기한다. 고정 시드42도 새 엔진에서 다시 적용하므로 첫 부품의 결과는 반복 실행에서도 동일하게 결정된다. 20개 연속 생산·대기열 경합·고장/복구·이력 저장은 후속 범위다.
