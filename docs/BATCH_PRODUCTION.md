# 소재 20개 연속 생산과 입력 대기열

작성일: 2026-10-10 (Asia/Seoul)  
상태: 코드·문서 작성 완료, 사용자 확인 대기. 테스트·빌드·린트·설치·서버 실행·HTTP 요청·브라우저 검증은 수행하지 않았다.

2026-10-10 후속: [설비 고장·복구](C:/project/truckworks/docs/STATION_FAULTS.md)를 연결했다. 현재 응답은 schema5다. 아래26초/178초·정상 완료 상태는 고장 없이 실행한 기준이며, 고장이 있으면 지연이 추가되고 완료 후 잔여 고장 표시가 남을 수 있다.

## 이번 구현 범위

기존 확정 규칙에 따라 소재20개를 ST-01에서 순서대로 투입한다. 각 설비는1개씩 처리하며 여러 설비는 동시에 동작한다. 처리시간2·8·6·4·2초와 구간 이동1초를 유지한다. 입력 대기는 FIFO이며 설비마다 `도착한 대기 부품 + 이동 중 예약 부품 ≤ 3`이다. 가공 중/출력 대기 부품은 이3개에 포함하지 않는다.

다음 설비의 입력 자리를 확보할 수 없으면 완료 부품을 현재 설비에 남기고 BLOCKED로 표시한다. 자리가 생기면 이동을 시작하고 현재 설비는 다음 부품을 처리한다. 이동은 별도 SimPy 프로세스로 이어져 이전 설비를 계속 점유하지 않는다. 입력 대기에서 가공을 시작할 때 예약/대기용 자리를 반환한다.

ST-01은 소재 재고에서 작업을 시작할 때1개씩 소비한다. 소재가 모두 투입된 뒤에도 남은 차체를 처리하며,20개 모두 적재돼야 COMPLETED다. 양품/불량 보관 용량은 확정된 각각20개로 전체20개를 수용한다. 보관품을 꺼내거나 별도의 작은 보관 용량을 조절하는 기능은 없다.

품질은 시드42로 생산 번호 순서에 따라 시작 시 한 번 정하고 ST-04 완료 때 공개한다. 품질 검사와 실제 적재 수량 증가 시점은 다르다. 고장/복구는 후속 작업에서 코드 작성했고 사용자 확인 대기다. 강제 불량 지정·이력 영속 저장은 아직 구현하지 않았다.

## 화면과 API

생산 시나리오에서 `차체 20개 연속 생산` 또는 기존 `차체 1개 전체 공정 / 26초`를 선택한다. 실행 중 선택은 잠기며 초기화 후 다시 고를 수 있다. 이전 ST-01 단독 API도 유지한다. 기존 [일시정지·재개·초기화](C:/project/truckworks/docs/EXECUTION_CONTROLS.md)는 전체 실행에 적용한다.

새 시작은 `POST /api/factory/batch/start`이며 본문은 다음과 같다.

```json
{"expected_run_id":"현재 GET /api/factory/state의 run_id"}
```

중복 시작·이전 ID는409다. 상태·이벤트 조회는 기존 GET을 사용한다. 연속 생산 도입 당시 schema_version은4였으며 현재는 고장 전 상태·이벤트 part_id=null 추가로5다. model_version은chassis-line-v2이며 확정된 치수·공정 설정은 유지했다.

| 필드 | 의미 |
|---|---|
| scenario | 연속 생산에서는 batch |
| parts | 실제 투입한 부품 목록. 적재 후에도 유지하며 최대20개 |
| transfers | 현재 이동 중인 부품별 구간/진행률 |
| part / transfer | 기존1개 시나리오용 필드. batch에서는null |
| production_number | 실행 내 생산 번호1~20. UUID는 별도로 유지 |
| part.phase | PROCESSING / BLOCKED / TRANSFERRING / QUEUED / STORED |
| queued_part_ids | 실제 도착한 입력 대기 부품의 FIFO 순서 |
| reserved_part_ids | 이동 중 확보한 입력 자리 |
| counts.in_process_count | 투입 후 미적재 부품 전부. 가공·이동·입력/출력 대기를 포함 |
| counts.waiting_count | 실제 입력 대기 부품만 합산. in_process_count의 부분집합 |

항상 `소재 잔여 + 라인 내부 + 양품 + 불량 = 20`이어야 한다. 입력 대기 수량을 여기에 다시 더하면 이중 계산이다. 아직 투입하지 않은 소재를 parts나 입력 대기로 꾸며서 표시하지 않는다.

우측에서 생산 번호별 차체를 선택해 ID·가공 단계·품질·위치를 추적한다. 설비 상세와3D 라벨에 실제 입력 대기·이동 예약 수를 표시하고 이벤트에 차체 번호를 표시한다. RUN_PAUSED·RUN_RESUMED·RUN_COMPLETED는 전체 실행의 이벤트이며 응답의 part_id/station_id는 대표 부품의 문맥이다.

3D는 가공 부품·이동 부품·입력 대기 묶음·판정별 보관 묶음을 각 부품 ID로 표시한다. 입력 대기와 보관은 개수를 읽기 위한 도식적 쌓기이며 실제 장비 적재 구조·물리 모델이 아니다.2D 배치도는 기존 정적 선택 화면이다.

## 사용자가 직접 확인할 절차와 기대 결과

새 의존성은 없다. 백엔드를 재시작하고 프론트엔드를 새로고침한다. 서버 실행 명령은 [backend README](C:/project/truckworks/backend/README.md)를 따른다.

1. 초기 READY·소재20·모든 수량0·빈 parts/transfers/events를 확인한다.20개 생산을 시작하면 첫 소재를 소비하고 차체 #1이 생성돼야 한다.
2. ST-01은2초, ST-02는8초이므로 ST-02 입력 대기가 쌓여야 한다. 기본 시나리오의10초 부근에는 ST-01의 다섯 번째 차체가 완료돼 BLOCKED, ST-02는 가공1개·입력 대기3개가 기대 결과다. 조회 간격에 따라 표시 시각에 차이가 있을 수 있다.
3. ST-02가 다음 차체의 가공을 시작하면 자리가 반환되고 ST-01의 BLOCKED가 풀려야 한다. OUTPUT_BLOCKED/OUTPUT_UNBLOCKED 이벤트가 같은 차체 ID로 짝지어져야 한다. PROCESS_COMPLETED가 해제 때 다시 기록되면 안 된다.
4. ST-02의 PROCESS_STARTED 이벤트에서 생산 번호가 순서대로 진행되는지 확인한다. 모든 설비에서 `대기 수 + 예약 수 ≤ 3`과 현재 부품 최대1개가 유지돼야 한다. 도착 예약은 도착 시 입력 대기로 바뀌고, 가공 시작 시 입력 대기에서 빠져야 한다.
5. 가공·이동·입력 대기·출력 대기가 함께 있는 시점에 일시정지한다. 시각·모든 가공 잔여시간·이동 진행률·각 부품 ID·대기/예약 순서가 유지돼야 한다. 재개 후 전체가 남은 시간부터 이어져야 한다.
6. 수량 보존식을 중간 상태에서도 확인한다. 부품 UUID가 설비/대기/이동에 중복 배치되면 안 된다. 각 차체는 공정마다 시작/완료1회·검사1회·적재1회만 기록돼야 한다.
7. 기본 공정 시간으로 첫 적재26초, ST-02의8초 간격을 따라 마지막 적재178초가 기대 결과다. 일시정지한 실제 시간은 시뮬레이션 시간에 더하지 않는다. 완료 시 소재0·라인 내부0·입력 대기0·양품+불량20·parts20개 모두STORED·transfers없음·모든 설비IDLE·빈 대기/예약이어야 한다. 이는 명세/코드에서 예상한 결과이며 실행 측정값이 아니다.
8. 초기화를 실행 중·일시정지 중·완료 후 각각 수행한다. 새 run_id·소재20·빈 parts/transfers/events로 복원되고 이전 명령은409여야 한다. 새 생산에 이전 실행의 차체·타이머가 섞이면 안 된다.
9. 초기화 후1개 시나리오도 선택해26초 흐름과21개 기본 이벤트를 확인한다. 기존 [단일 공정](C:/project/truckworks/docs/SINGLE_STATION.md)과 [차체1개](C:/project/truckworks/docs/SINGLE_PART.md) API도 유지돼야 한다.

연속 생산 이벤트에는 MATERIAL_LOADED·QUEUE_ENTERED/QUEUE_LEFT·출력 대기 이벤트가 추가되므로 기존1개 시나리오의21개를 전체 이벤트 수로 사용하지 않는다. 순번은 같은 run_id에서 계속 증가하고 RUN_COMPLETED는 마지막 적재 후1회여야 한다. 새로고침과 재연결은 서버의 현 상태를 다시 표시해야 한다.
