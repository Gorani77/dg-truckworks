## 이번 범위와 확정 사항

사용자가 공정 사이 이동을 구간당 1초로 선택했다. 처리 2·8·6·4·2초와 이동 4회를 합해 총 26초다. 소재 20개 중 1개만 생산한다. COMPLETED는 이 1개 시나리오 완료이며 20개 전체 생산 완료가 아니다.

| 시뮬레이션 시간 | 동작 | 부품 형태 |
|---|---|---|
| 0–2초 | ST-01 소재 투입 | RAW 소재 |
| 2–3초 | ST-01 → ST-02 이동 | 소재 |
| 3–11초 | ST-02 형상 가공 | 11초 완료 때 FRAME |
| 11–12초 | ST-02 → ST-03 이동 | 프레임 |
| 12–18초 | ST-03 구멍 가공 | 18초 완료 때 DRILLED |
| 18–19초 | ST-03 → ST-04 이동 | 구멍 가공 차체 |
| 19–23초 | ST-04 품질 검사 | 23초 완료 때 품질 공개 |
| 23–24초 | ST-04 → ST-05 이동 | 판정 차체 |
| 24–26초 | ST-05 분리·적재 | 판정에 맞는 보관 위치로 표시 |
| 26초 | COMPLETED | STORED, 모든 설비 IDLE |

실행 시작에 Random(42)와 불량 확률 0.05로 부품 1개의 결과를 한 번 정하고 검사 완료 시 공개한다. 검사 전 part.quality는 UNINSPECTED다. 기본 설정의 첫 부품은 양품이 기대 결과이며 1개 실행에서 반드시 불량이 나오는 것은 아니다. LLM·비전 AI 판정이나 강제 불량 기능은 없다.

소재 소비 후부터 적재 전까지 소재 잔여 19·라인 내부 1·양품/불량 0을 유지한다. 적재 완료 때만 라인 내부가 0이 되고 양품 또는 불량이 1 증가한다. 항상 소재 잔여 + 라인 내부 + 양품 + 불량 = 20이다. 입력 대기 수량은 0이다.

다음 설비의 reserved_part_ids에 동일 부품 ID를 예약한 뒤 이동한다. 이동 중 예약은 실제 입력 대기 수량으로 세지 않고 도착 시 해제한다. 단일 부품이므로 실제 대기열 포화·경합·여러 부품 FIFO를 구현한 것은 아니다.

## API와 응답

- 새 시작: `POST /api/factory/single-part/start`, 본문은 `{"expected_run_id":"현재 run_id"}`.
- 기존 상태·이벤트 GET을 사용한다. 이전 ST-01 단독 POST `/single-station/start`도 유지한다.
- 같은 실행에서는 두 시나리오 중 하나만 한 번 시작할 수 있다. 중복·이전 실행 ID는 409다.
- 전체 공정 도입 당시 schema_version은2, 실행 제어 추가 때3이었다. 현재는 연속 생산 parts/transfers 추가로4이며 model_version은chassis-line-v2다. 전체 공정 필드는 scenario·part·transfer와 설비 reserved_part_ids다.
- part는 ID·가공 단계·진행 단계·공개된 품질·현재 설비 또는 보관 위치를 담는다. 단독 ST-01 시나리오는 기존과 같이 part/transfer가 null이다.
- transfer는 출발/도착 설비·시작 시각·1초 duration·0~1 progress다. 이동 외에는 null이다.
- 제어 없는 실행의 이벤트21개: 공정 시작/완료 각5개, 이동 시작/도착 각4개, 품질 공개·보관·시나리오 완료 각1개. 모두 같은 run_id·part_id다. 일시정지·재개 한 쌍마다 이벤트2개를 추가한다.

기존 단일 worker·메모리 보관 구조를 유지한다. 서버 재시작·개발 reload는 새 실행으로 초기화한다. HTTP 조회 반복을 유지하며 WebSocket·DB는 없다.

## 3D와 화면

화면 시작 버튼은 새 전체 공정 API를 호출한다. 현황에 COMPLETED를 `차체 1개 완료`로 표시하고 우측 `차체 추적`에 동일 부품 ID·형상 단계·품질·위치를 표시한다. 설비 상세에는 이동 도착 예약 수를 표시한다.

실제 부품은 하나의 PartModel로 렌더링한다. 설비마다 복제하지 않는다. 이동 위치는 서버 transfer.progress, 적재 동작의 표시 위치는 ST-05 남은 시간에 따른 공정 진행률에서 계산한다. 화면은 최신 서버 위치까지만 부드럽게 보간하며 서버 시간을 별도로 진행하지 않는다. 구멍은 레일 Shape의 holes와 ExtrudeGeometry로 표현했다. 구멍 크기·위치는 도식적 시각화이며 미확정 제작 치수를 확정한 것은 아니다.

별도의 형상 참고 프레임 표시는 유지한다. 부품의 판정 색은 검사 결과 공개 후에만 바뀐다. 도구 움직임은 서버 PROCESSING 상태에 연결한 설명용 표현이며 실제 기계 운동·운반 물리를 재현하지 않는다. 2D 배치도는 정적 선택 화면이며 실제 이동 표현은 3D에서 제공한다.

## 사용자 실행·확인

새 패키지는 추가하지 않았다. 이전 SimPy·3D 패키지 설치를 마쳤다면 재설치는 필요 없다. 백엔드를 재시작해 schema4와 새 실행을 받고 프론트엔드를 새로고침한다. 이번1개 흐름을 확인할 때는 시나리오에서1개를 선택한다. 아직 설치하지 않았다면 기존 SINGLE_STATION.md·FACTORY_3D.md의 uv sync·npm install 안내를 따른다.

```powershell
# C:\project\truckworks\backend에서 실행
& "$env:APPDATA\Python\Scripts\uv.exe" run uvicorn truckworks.api.app:create_app --factory --reload --host 127.0.0.1 --port 8010
```

1. 시작 전 READY·소재 20·수량 0·part/transfer null·빈 이벤트를 확인한다.
2. `차체 1개 생산 시작`을 누른다. 소재는 19, 라인 내부는 1이 되고 위 시간표로 처리·이동해야 한다.
3. 우측 차체 추적·이벤트·3D에 동일 부품이 이어지는지 확인한다. 양품/불량은 검사 전 0이며 품질은 검사 전 공개되지 않아야 한다.
4. 26초에 시간 고정·차체 1개 완료·모든 설비 IDLE·예약 해제·라인 내부 0·양품 1(기본 시드)이 기대 결과다. 부품은 양품 적재함에 남아야 한다.
5. `/api/factory/events`에서 순번 1~21·동일 part_id, last_event_sequence 21을 확인한다. 반복 GET으로 값이 증가하지 않아야 한다.
6. 처리 중·완료 후 시작 버튼은 비활성화된다. API 문서에서 같은 시작을 재전송하면 409이고 소재 추가 소비·이벤트 중복이 없어야 한다.
7. 화면 새로고침은 현재 생산·완료 상태를 다시 표시해야 한다. 서버 재시작은 새 run_id·초기 상태로 돌아오고 이전 ID는 409다.
8. 카메라 회전·공정 선택·2D 전환·재연결도 확인한다. 시작 전에 이전 단독 API를 실행했다면 실행 초기화 후 전체 시나리오를 시작할 수 있다.

확인 방법과 기대 결과이며 수행 결과가 아니다. Codex는 테스트·빌드·린트·서버 실행·HTTP 요청·브라우저 검증을 수행하지 않았다.
