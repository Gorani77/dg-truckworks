## 이번에 추가한 내용

기존 PostgreSQL에 분석 접수·성공·실패·시간 초과·실행 변경·서버 작업 취소 결과를 저장한다. 질문, 관측 실행/버전/시각, 사용 도구와 자료, 답변/근거, 확인된 사용량과 추정 비용을 보관하고 화면의 별도 분석 이력에서 수동 조회한다. 조회로 OpenAI를 호출하거나 현재 공장을 변경하지 않는다.

분석 작업을 접수한 뒤 RUNNING 기록과 종료 기록을 비동기 저장 작업자에게 넘긴다. 같은 분석 ID는 최신 revision으로 합치고 DB에서는 이전 revision이 최신 결과를 덮지 않도록 한다. 생산 저장 작업자와 분리했으며 생산 실행 행의 커밋 순서 때문에 분석 저장이 실패하지 않도록 run_id는 외래 키가 아닌 관측 식별자로 보관한다.

입력 오류·키 미설정·실행 ID 불일치·선택 설비 없음·동시 요청/간격 제한처럼 분석 접수 전 거절한 요청은 기록하지 않는다. 모델 요청 전 거절을 실제 유료 분석처럼 세지 않는다.

## 사용량을 읽는 방법

기존에는 그래프가 끝난 성공 응답만 사용량을 볼 수 있었다. 이제 그래프 밖의 UsageLedger가 API 요청 직전 model_calls를 늘리고, 응답을 받으면 종료 상태·답변 형식을 검사하기 전에 사용량을 수집한다. 첫 응답 뒤 두 번째 요청이 실패해도 첫 응답의 토큰은 보존된다. incomplete 응답에서 사용량을 받았다면 그 수치도 보존한다.

- model_calls: 시도한 모델 요청 수.
- reported_calls: 실제 사용량을 수신한 응답 수.
- input_tokens·cached_input_tokens·output_tokens: 수신한 사용량 합계.
- usage_complete: 시도한 모든 요청의 사용량을 수신했는지 여부. 실제 청구와 일치한다는 검증 표식이 아니다.
- estimated_cost_usd: 확인된 토큰에 기존 기본 모델 단가를 적용한 추정치. 다른 모델은null이다.

예를 들어 첫 응답 사용량을 받은 뒤 두 번째 요청에서 통신이 끊기면 model_calls=2·reported_calls=1·usage_complete=false다. 화면은 ‘집계 불완전 · 최종 비용 알 수 없음’과 확인된 토큰의 비용만 표시한다. 첫 요청부터 사용량을 받지 못하면 숫자0을 실제 비용0으로 안내하지 않고 ‘수신 사용량 없음’으로 표시한다. 공급자 청구 확인은 별도다.

## 저장 상태와 기록 해석

| 상태 | 의미 |
|---|---|
| RUNNING | 마지막 저장에 완료 결과가 없음. 실제 현재 분석 중일 수도 있고 강제 종료로 남았을 수도 있음 |
| SUCCEEDED | 답변과 근거 존재 검사까지 처리하고 기존 실행에 응답함 |
| FAILED | 접수 후 모델/형식/근거/내부 처리에서 실패 |
| TIMED_OUT | 전체 제한 또는 SDK 시간 초과 |
| STALE | 답변 처리 중 공장 실행 ID가 바뀌어 현재 결과로 반환하지 않음 |
| CANCELLED | 서버 분석 작업이 CancelledError로 취소됨. 브라우저 취소와 반드시 같지 않음 |

STALE의 답변이 저장돼 있으면 이전 관측에 대한 과거 자료로만 읽는다. 저장 시점의 RUNNING을 현재 실행 중으로 표시하거나 자동으로 FAILED로 변경하지 않는다. 브라우저 요청 취소가 서버 작업 취소·원격 과금 취소까지 보장하지 않는다.

성공/실패 응답에는 접수한 분석 ID를 X-Analysis-ID 헤더로 제공한다. 저장이 설정돼 있으면 X-Analysis-History=queued이며 이는 메모리 저장 대기에 제출했다는 뜻이다. DB 커밋 완료는 이력 조회에서 확인한다. 모델 응답 성공과 저장 성공을 구분한다.

저장 대기는 메모리다. DB 장애 때2초 간격 재시도하고 정상 종료 때 최대5초 기다린다. 강제 종료·장기 DB 장애로 미저장 자료가 유실될 수 있으며 무손실 outbox는 미구현이다. 생산 이력과 분석 이력의 대기/오류는 각각 표시한다.

## 민감값과 보관 경계

서버에 설정된 실제 키·DB URL, sk- 형태의 키·Bearer 값·자격 증명이 포함된 URL, 민감한 이름의 JSON 필드는 DB 저장 대기에 넣기 전에 마스킹한다. 질문·답변·도구 인자/결과에 같은 처리를 적용한다. 알려진 패턴 마스킹은 임의의 개인정보까지 자동 판별하는 기능이 아니다. 질문에 민감정보를 넣지 않고 공장 상태만 질문한다. 원본 공급자 오류나 내부 추론 메시지는 이력에 저장하지 않는다.

서버 메타데이터 로그에는 ID·모델·실행·상태·요청/사용량 수신 수·토큰만 기록한다. 질문/답변 전문을 로그에 추가하지 않는다. DB에는 조회용으로 마스킹된 질문/답변/도구 자료를 보관하는 것이 이번 단계의 변경이다. 키 설정이나 값은 문서에 기록하지 않는다.

## API와 화면

- GET /api/analysis/status: 기존 모델 설정 상태에 history_enabled·history_pending·history_error 추가. 활성 설정만으로 연결 성공을 뜻하지 않는다.
- GET /api/analysis/history?run_id=UUID&limit=20&offset=0: 실행 필터 선택, 최신순, limit최대100.
- GET /api/analysis/history/{analysis_id}: 저장된 전체 관측·도구·답변·사용량. 미설정/DB 오류503·없는 기록404·잘못된 입력422.
- 화면 ‘분석 이력’: 현재 실행 필터·이전 실행 포함·20개 페이지·상세·사용량·저장 대기/오류. 수동 새로고침만 수행한다. 초기화 시 기존 요청/선택은 정리하며 이전 실행 포함으로 과거 기록을 다시 읽을 수 있다.

## 사용자가 직접 확인할 절차와 기대 결과

1. 마이그레이션·서버 재시작·화면 새로고침 후 정상 질문을 직접 요청한다. 분석 ID가 표시되고 저장 대기 해소 후 이력 새로고침에서 동일 ID·질문·관측 버전·도구·답변·근거·사용량이 조회돼야 한다.
2. 공장을 초기화하고 ‘이전 실행 포함’을 선택한다. 이전 분석이 남고 해당 run_id와 관측 자료를 표시하며 현재 생산에는 영향이 없어야 한다.
3. 서버/DB 정상 재시작 후 같은 기록을 조회한다. 저장된 성공/실패 자료가 유지되고 조회가 OpenAI 요청을 만들면 안 된다.
4. 필요하면 잘못된 키나 모델 설정으로 접수 후 실패를 직접 확인한다. 원본 오류·실제 키가 DB 이력/오류 메시지에 남지 않고, 사용량 미수신을 비용0으로 표시하지 않아야 한다. 설정을 복구한 뒤 서버를 재시작한다.
5. 첫 응답 뒤 다음 요청 실패·시간 초과 상황을 직접 재현할 경우 첫 응답의 토큰은 남고 미수신 요청은 집계 불완전이어야 한다. 재현을 위한 자동 실패 주입 기능은 추가하지 않았다.
6. DB를 중단한 상태에서 분석을 요청하면 모델 결과와 별도로 저장 대기/오류가 표시돼야 한다. DB 복구 후 같은 ID가 중복 없이 최종 revision으로 저장돼야 한다. 실패 재현에도 OpenAI 비용이 발생할 수 있다.
7. 초기화 중 분석은STALE, 서버 작업 취소가 실제 발생하면CANCELLED를 확인한다. 강제 종료로 남은 RUNNING은 완료 정보 없음으로 표시해야 한다. 실제 종료 타이밍에 따라 접수 기록까지 미저장일 수 있다.
8. API의 없는 분석 ID404·DB 미설정503·잘못된 UUID/limit422를 확인한다. 이전 기능 확인 대기는 이 작업으로 완료 처리하지 않는다.

다음은 사용자 결과 반영과 공개 전 비용/접근 제한이다. 계정 전체 예산 차단·인증/사용자별 제한·내구성 있는 저장 대기·자동 평가·과거 실행 분석은 아직 구현하지 않았다.
