# 유휴 공장 30분 정리

2026-10-10 (Asia/Seoul). 사용자 선택: 열린 연결과 처리 중인 요청은 유지하고, 연결도 API 요청도 없는 공장은 30분 뒤 종료한다. 코드·문서 작성 완료, 사용자 확인 대기다. 테스트·빌드·린트·설치·서버 실행·HTTP·브라우저 검증은 수행하지 않았다.

## 적용 규칙

- 기준은 마지막 연결/요청이 끝난 뒤의 실제 경과 시간이다. 시뮬레이션 시간과 별개로 monotonic 시계를 사용한다.
- WebSocket이 하나라도 열려 있거나 HTTP/분석 요청을 처리 중이면 공장을 정리하지 않는다. 여러 탭 중 하나만 열려 있어도 유지한다. 화면이 열려 있다는 기준은 실제 소켓 연결이며 네트워크 단절 뒤 열린 탭만 남은 경우에는 적용되지 않는다.
- 마지막 연결/요청이 끝나면 유휴 시간이 시작된다. 이후 API 요청이나 세션 준비 요청이 있으면 다시 활동으로 계산한다. 생산 runner의 자체 진행이나 DB 저장은 방문자 활동으로 계산하지 않는다.
- 기본 `TRUCKWORKS_VISITOR_IDLE_SECONDS=1800`이고 30초마다 정리 후보를 찾는다. 따라서 정확히 30분에 종료하는 타이머가 아니라 유휴30분 이상이 된 뒤 다음 검사에서 종료한다.
- READY·RUNNING·PAUSED·고장·COMPLETED 상태 모두 같은 기준이다. 화면을 닫았다고 바로 생산을 멈추지는 않지만, 유휴 기준에 도달하면 진행 중/고장/일시정지 공장도 종료한다.
- 종료할 엔진을 registry에서 먼저 분리하고 runner 진행 task를 취소한 뒤 마지막 상태와 누적 이벤트를 기존 저장 큐에 `IDLE_EXPIRED`로 제출한다. 저장 설정이 없으면 DB 보관은 없고, 저장 설정이 있어도 큐 제출과 커밋은 다르다. 기존 메모리 저장 큐의 강제 종료 손실 가능성은 유지한다.
- 같은 쿠키로 돌아오면 새 run_id·READY·소재20개를 받는다. 소유권 쿠키는 변경하지 않아 기존 DB 이력을 계속 조회한다. 이전 엔진의 남은 가공을 복구/재개하지 않는다.
- 저장 당시 run_status가 RUNNING/PAUSED일 수도 있다. `IDLE_EXPIRED`는 종료 이유이며 정상 생산 완료를 뜻하지 않는다. 화면에서는 `유휴 공장 정리로 보관`으로 표시한다.

추가 이용 횟수·지출·접근 횟수 제한은 없다. 유휴 공장 메모리를 정리하는 정책이며 DB 기록 보존 기간을 줄이지 않는다. 다중 worker나 프로세스 간 엔진 공유는 이번 범위가 아니다.

## 구현 흐름

`dependencies.get_visitor`가 yield 동안 active_requests를 유지한다. HTTP와 WebSocket이 같은 경로를 쓰므로 요청/연결 종료·오류에도 finally에서 감소하고 마지막 활동 시각을 갱신한다. `POST /api/session`도 resolve에서 활동을 기록한다.

`VisitorRegistry._collect_idle`는 사용 중인 수가0이고 마지막 활동이 기준을 넘은 엔진만 분리한다. 검사와 삭제 사이에는 await가 없다. 이전 엔진의 종료는 별도 task이며 새 방문자가 들어와도 새 run_id의 엔진과 섞이지 않는다. 서버 종료 때 정리 루프를 먼저 멈추고 이미 진행 중인 유휴 종료와 나머지 엔진 종료를 기다린다. 이후 기존 저장 작업자를 종료한다.

`SimulationRunner.close`는 종료 이유를 받아 기본 SERVER_STOP 또는 IDLE_EXPIRED를 기존 이력 저장 경로로 전달한다. 새 의존성이나 DB migration은 없다. 이전 방문자 소유권 기능의0003 migration 적용은 여전히 필요하다.

## 사용자가 직접 확인하는 순서

1. 기본30분 정책은 서버 재시작으로 적용된다. 새 migration/패키지 설치는 없다. 이전 기능 미적용 항목은 기존 문서를 따른다.
2. 시간을 줄여 확인하려면 백엔드를 실행할 PowerShell에서만 `$env:TRUCKWORKS_VISITOR_IDLE_SECONDS="15"`로 설정한 뒤 기존 서버 명령으로 시작한다. 기존 서버와 포트가 겹치지 않게 먼저 중단한다. 로컬 비밀키 파일은 변경할 필요 없다. 이 값은 직접 확인용 임시 값이며 제품 기본값은1800이다.
3. 화면을 열고 run_id를 적는다. 일시정지해 두거나 READY에서 45초 이상 화면을 유지한다. 소켓이 살아 있으면 run_id가 그대로여야 한다. 다른 방문자의 별도 브라우저도 독립적으로 유지된다.
4. 같은 프로필에서 새 탭을 열고 원래 탭만 닫는다. 남은 탭이 연결된 동안45초 이상 기다려도 동일 실행이어야 한다.
5. 모든 TruckWorks 탭을 닫되 쿠키가 사라지지 않도록 브라우저 자체는 다른 빈 탭으로 켜 둔다. 다른 도구에서도 같은 쿠키로 API 요청을 보내지 않는다. 최소45초가 지난 뒤 다시 열면 새 run_id·READY·소재20개여야 한다. 검사 주기 경계와 연결 해제 감지 때문에 여유를 더 둘 수 있다.
6. DB 사용 시 생산 이력 새로고침으로 이전 실행의 `유휴 공장 정리로 보관`을 확인한다. 동일 쿠키의 기존 생산·분석 이력을 계속 읽을 수 있어야 한다. 정상 완료/초기화와 유휴 종료 표시를 구분한다.
7. 요청도 활동으로 계산하는지는 아래처럼 브라우저 없이 같은 PowerShell WebRequestSession을 재사용해 확인할 수 있다.15초보다 짧은 간격의 상태 조회를 이어가면 실행이 유지되고, 요청 없이45초 이상 지난 뒤 조회하면 새 실행이어야 한다. 조회 중에 서버를 다시 시작하면 별개의 재시작 효과가 생기므로 이 확인 중에는 재시작하지 않는다.

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8010/api/session -SessionVariable truckworksSession
Invoke-RestMethod -Uri http://127.0.0.1:8010/api/factory/state -WebSession $truckworksSession
```

8. 실제 모델 분석 중 유지 확인은 사용자가 원할 때만 요청한다. 요청이 처리 중인 동안 엔진을 정리하면 안 된다. 원격 API 비용은 발생할 수 있으며 유휴 정리 때문에 자동 재호출하지 않는다.
9. 확인 후 서버를 중단하고 `Remove-Item Env:TRUCKWORKS_VISITOR_IDLE_SECONDS`로 임시 환경변수를 제거한 뒤 재시작한다. 별도로 기존 .env에 값을 설정해 둔 경우 그 설정이 적용되므로 기본1800 기준으로 맞춘다. 실제 기본 정책 확인은 연결/요청 없는30분과 검사 여유30초 이상을 기다린다.

확인 결과를 받기 전에는 이 기능을 실행 검증 완료로 기록하지 않는다. 구현 참고: [FastAPI yield 의존성의 수명과 finally](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/).
