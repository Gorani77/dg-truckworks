# 설비 수동 고장·복구

> 후속 이력 저장 작업에서 현재 응답은 schema6으로 바뀌었고 이벤트 occurred_at을 추가했다. 고장 규칙은 유지하며 DB 준비·저장·조회는 [이력 저장 안내](C:/project/truckworks/docs/HISTORY_STORAGE.md)를 따른다. 아래 영속 저장 미구현 설명은 고장 기능 작성 시점의 범위다.

작성일: 2026-10-10 (Asia/Seoul)  
상태: 코드·문서 작성 완료, 사용자 확인 대기. 테스트·빌드·린트·설치·실행·HTTP 요청·브라우저 검증은 수행하지 않았다.

## 동작과 범위

생산을 시작하고 공정 목록이나3D에서 설비를 선택한 뒤 `고장 발생`을 누른다. 선택한 설비만 FAULTED가 되며, 공장 실행 상태는 RUNNING을 유지한다. 시뮬레이션 시계·다른 설비·이동은 계속 진행한다. 고장 때문에 뒤쪽 공간이 차면 정상 설비도 출력 대기에 들어갈 수 있다. 이것은 추가 고장이 아닌 공간 부족이다.

- 가공 중: 같은 부품·가공 단계·품질과 남은 시간을 유지한다. 복구 후 남은 시간부터 처리하며 공정 시작을 다시 기록하지 않는다.
- 입력을 기다리던 설비: 새 가공을 시작하지 않는다. 이미 출발한 차체는 도착해 입력 대기에서 기다린다. 대기+이동 예약≤3을 유지한다.
- 출력 BLOCKED 중: 가공 완료 부품과 남은 시간0을 유지한다. 고장 중에는 다음 공간을 새로 확보해 출발하지 않는다. 복구 후 공간을 확보하고 이동하며 가공 완료를 재기록하지 않는다.
- 가공 중이 아닌 설비: 고장 이벤트의 part_id는null일 수 있다. 존재하지 않는 부품을 이벤트에 만들어 넣지 않는다.
- 공장 일시정지 중: 고장·복구 명령은 가능하다. 복구해도 작업·이동·FIFO 이동·소재 소비는 공장 재개 전까지 진행하지 않는다. 공장 재개만 눌러도 설비 고장은 유지된다.
- 완료 후: 새 고장은 거절한다. 완료 전에 생긴 잔여 고장은 복구할 수 있고 초기화로도 제거된다. 완료됐다고 사용자가 발생시킨 고장을 자동으로 지우지 않는다.

고장 자체로 불량을 만들지 않는다. 시작 때 고정 시드로 정한 검사 결과를 유지하고 검사 완료 후에만 공개한다. 자동 고장·강제 불량·고장 통계/영속 저장은 추가하지 않았다. 기존 단독 ST-01·차체1개·20개 엔진 모두 공통 가공 중단 로직을 사용한다.

차체1개 시나리오에서도 고장 난 다음 설비로 도착하면 QUEUED·입력 대기1개로 표시하고 복구를 기다린다. 정상 실행의26초는 유지하지만 설비 고장으로 실제 시뮬레이션 지연이 생기면26초를 넘겨 완료한다.20개 기본178초도 고장 없는 기준이다. 공장 일시정지의 실제 대기 시간은 시뮬레이션 시각에 더하지 않는다.

## API와 응답

현재 schema_version은5다. 설비에 `status_before_fault`를 추가해 고장 직전 PROCESSING·IDLE·BLOCKED를 보관하고, 복구 후에는null로 비운다. 생산 이벤트의 part_id는부품 없는 설비 고장/복구에서null을 허용한다. 기존 model_version·생산 설정은 유지한다.

| 명령 | 경로 | 허용 조건 |
|---|---|---|
| 고장 | POST /api/factory/stations/ST-02/fault | RUNNING 또는 사용자 PAUSED, 선택 설비가 정상 |
| 복구 | POST /api/factory/stations/ST-02/repair | 선택 설비가 FAULTED. 완료 후에도 가능 |

ST-02 대신 실제 선택 설비 ID를 넣는다. 두 명령의 본문은 `{"expected_run_id":"현재 run_id"}`다. 응답은 공장 상태 전체다. 존재하지 않는 설비·중복 고장·정상 설비 복구·잘못된 실행 상태·이전 run_id는409이며 잘못된 UUID/추가 본문 필드는422다. 명령은 자동 재전송하지 않으며 실패 후 상태 조회를 재개한다.

고장/복구마다 STATION_FAULTED·STATION_RECOVERED 이벤트를 각1개 기록한다. 가공 중이면 해당 part_id를, 부품이 없으면null을 기록한다. 상태·이벤트의 시뮬레이션 시각은 명령 시각을 사용한다. 완료와 고장 명령이 맞물리면 명령 시각까지 공정을 진행한 후 상태를 판정한다.

## 사용자가 직접 확인할 절차와 기대 결과

새 의존성은 없다. 백엔드 재시작·화면 새로고침 후 아래 순서로 확인한다. 상세 생산 시간표는 [1개 생산](C:/project/truckworks/docs/SINGLE_PART.md), 대기 규칙은 [20개 생산](C:/project/truckworks/docs/BATCH_PRODUCTION.md)을 참고한다.

1. **가공 중 고장:**20개 생산 시작 후 ST-02 가공 중 고장을 발생시킨다. FAULTED·고장 전 PROCESSING·동일 current_part_id·고정된 남은 시간이 기대 결과다. 몇 초 기다려도 고장 설비의 잔여시간은 줄지 않아야 한다. 시계와 다른 설비/이동은 계속 진행하고, ST-02 앞 대기가 차면 ST-01이 BLOCKED가 돼야 한다.
2. **가공 복구:**같은 설비를 복구한다. status_before_fault는null이 되고 남은 작업부터 이어져야 한다. 해당 차체의 PROCESS_STARTED/PROCESS_COMPLETED·검사·적재가 중복되면 안 된다. 고장/복구 한 쌍의 이벤트는 각1개다.
3. **출력 대기 중 고장:**ST-01이 BLOCKED인 시점에 고장을 발생시킨다. 고장 전 BLOCKED·current_part_id 유지·남은 시간0을 확인한다. ST-02가 공간을 비워도 ST-01은 복구 전까지 출발하거나 다음 소재를 소비하면 안 된다. 복구 후 공간이 있으면 출발하고, 없으면 다시 BLOCKED로 기다린다. 이미 기록한 가공 완료는 반복하지 않는다.
4. **이동 목적지 고장:**1개 생산에서 ST-01 처리 중 ST-02를 선택해 고장을 발생시킨다. 첫 이동은2~3초에 계속되고,3초 도착 후 차체는 ST-02의 QUEUED·입력 대기1개·이동/예약 없음으로 기다려야 한다. 복구 후 ST-02의8초 처리를 시작한다. 이때 고장 시점에는 부품이 없으므로 해당 이벤트 part_id는null이 기대 결과다.
5. **전체 정지와 고장 조합:**가공 고장 후 공장 일시정지→설비 복구를 수행한다. 고장 표시만 해제되고 시각·잔여시간·대기/예약·소재 수량은 유지돼야 한다. 공장 재개 후 남은 작업이 진행돼야 한다. 반대로 고장 상태를 유지한 채 공장만 재개하면 해당 설비는 계속 FAULTED여야 한다.
6. **출력 대기+전체 정지 조합:**출력 BLOCKED일 때 공장 정지→해당 설비 고장→복구→공장 재개도 확인한다. 복구가 입력 공간 예약을 중복하거나 대기+예약3개 제한을 넘기면 안 된다. 정지 중 명령으로 소재 소비·부품 출발이 생기면 안 된다.
7. **반복·여러 설비:**복구한 설비에 다시 고장을 내거나 다른 설비에도 고장을 발생시킨다. 각 부품·잔여시간을 독립적으로 보존하고 복구해야 한다. 오래된 가공 timeout 시각이 지나도 고장 설비의 가공 완료가 나타나면 안 된다.
8. **수량·품질:**항상 소재 잔여+라인 내부+양품+불량=20, 대기+예약≤3을 확인한다. 고장 없는 실행과 생산 번호별 검사 결과가 같아야 하며 고장 자체로 불량이 증가하면 안 된다. 전량 복구·생산 완료 뒤 양품+불량은20이다. 고장으로 늘어난 완료 시각은 무조건178초로 고정하면 안 된다.
9. **오류·초기화:**중복 고장·정상 설비 복구·READY/COMPLETED에서 새 고장·잘못된 설비·이전 ID는409다. 고장 중 초기화하면 새 run_id·모든 설비IDLE·고장 전 상태null·빈 부품/이동/이벤트로 돌아가야 한다. 새 실행에 이전 timeout/복구 이벤트가 섞이면 안 된다.
10. **기존 흐름:**고장 없이1개26초·21개 이벤트,20개178초 기본 흐름과 공장 정지·재개를 다시 확인한다. 기존 ST-01 단독 API도 가공 중 고장·복구 후 남은 시간만 처리하고 종전 PAUSED/BLOCKED로 종료돼야 한다.

3D는 고장 표시등·진행 막대를 고장 색으로 표시하고 가공 도구를 마지막 수신 진행률의 위치에 둔다. 차체 추적·설비 상세·이벤트가 같은 고장을 설명해야 한다. 위치 보간이 마지막 서버 목표까지 잠깐 이어질 수 있으며 카메라 조작은 계속 가능하다.

## 구현을 읽는 순서

station_runtime.py의 `timeout | changed`는 가공 완료 또는 고장 신호를 기다린다. 고장으로 먼저 깨어나면 경과한 가공 시간만 빼고 복구를 기다린다. 기존 timeout이 나중에 발생하더라도 완료 처리는 이 가공 generator만 담당하므로 중복 완료하지 않는다. 완료 신호가 먼저면 잔여시간을 정확히0으로 둔다.

출력 공간 요청도 고장 신호와 함께 기다린다. 고장 시 미완료 요청을 취소하거나 이미 얻은 토큰을 반환하고 복구 후 다시 확보한다. 입력 Store에서 꺼낸 직후에도 고장 여부를 확인해 고장 중 도착한 차체의 입력 대기/자리 점유를 유지한다.

single_station.py는 공통 고장/복구 상태와 명령 시각 정렬을, single_part.py와batch.py는 각 흐름의 가공·대기 gate를 연결한다. runner와 API는 expected_run_id를 확인한 뒤 현재 시각까지 진행하고 명령을 적용한다. 프론트엔드는 수신 상태로 버튼·상세·3D를 표시한다. DB·여러 worker 간 상태 공유는 후속이다.
