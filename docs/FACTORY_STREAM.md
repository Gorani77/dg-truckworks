## 변경 내용

화면의 300ms HTTP 상태/이벤트 반복 조회를 `WS /api/factory/stream` 수신으로 바꿨다. 생산 제어 POST, 기존 GET 조회, DB 생산/분석 이력, OpenAI 분석 흐름은 유지한다. 이 연결은 OpenAI를 호출하지 않는다. 사용자 결정으로 추가 일일 횟수・지출・접근 제한은 도입하지 않고 기존 분석 요청별 보호 장치를 유지한다.

서버는 연결 직후 현재 상태를 보낸다. 생산 진행과 제어 변경 시 다음 JSON을 보낸다.

```json
{
  "type": "factory_state",
  "protocol_version": 1,
  "state": { "run_id": "실행 UUID", "state_version": 1, "last_event_sequence": 1 },
  "events": []
}
```

위 state는 설명용 일부 필드다. 실제로는 기존 FactoryStateResponse 전체와 같은 실행・마지막 순번 이하의 전체 누적 이벤트를 함께 보낸다. 이벤트 순번은 기존 스키마를 유지하고 transport protocol_version은 별도로 둔다.

- runner가 같은 이벤트 루프에서 await 없이 불변 상태와 이벤트 tuple을 포착한다. DB 설정 없이도 발행한다.
- 구독자 대기는 최대 1프레임이다. 느린 연결의 대기 프레임을 최신 것으로 교체한다. 전송 중 프레임은 별도이며 각 프레임에 누적 이벤트가 있으므로 중간 상태를 건너뛰어도 다음 수신에서 이벤트를 복원한다. 모든 중간 애니메이션 프레임의 전달을 보장하는 방식은 아니다.
- 생산 중 runner의 기존 100ms 진행에 따라 발행한다. 5초간 변경이 없으면 `{"type":"heartbeat","protocol_version":1}`을 보낸다. 프레임/heartbeat가 15초간 오지 않으면 브라우저가 연결을 다시 연다.
- 끊김/오류에는 현재 화면 데이터를 비우고 제어를 막는다. 1.5초부터 최대 10초 간격으로 자동 재접속한다. 유효한 상태를 받은 뒤 연결됨으로 표시한다.
- 같은 실행의 낮은 state_version은 무시한다. 초기화로 실행 UUID가 달라지면 새 상태와 이벤트로 교체한다. HTTP 제어 응답은 화면 상태를 덮어쓰지 않는다. 전송 실패한 생산 명령은 자동 재시도하지 않는다.
- 주소는 현재 웹 origin을 사용해 HTTP이면 ws, HTTPS이면 wss로 만든다. Vite는 `/api`에 `ws: true` 프록시를 사용한다. 배포 프록시도 WebSocket 업그레이드를 전달해야 한다.

WebSocket을 처음 작성할 때는 서버 공장 하나를 공유했다. 후속 방문자 분리에서는 같은 쿠키의 탭만 동일 실행을 본다. 다중 worker/서버 간 동기화·공개 호스팅은 아직 없다. 전체 누적 이벤트 방식은 현재 소재 20개 데모를 기준으로 작성했으며 장시간 무한 생산에는 별도 전송 설계가 필요하다.

## 사용자가 직접 진행할 순서

1. `C:\project\truckworks\backend`에서 `uv sync`로 추가한 websockets 의존성과 잠금 파일을 반영한다. uv가 PATH에 없으면 기존 안내의 uv.exe 절대 경로를 사용한다. 이번 기능에 새 DB migration은 없다. 이전 분석 이력 기능에는 기존 `uv run alembic upgrade head`가 필요하다.
2. 기존 백엔드 명령으로 서버를 다시 시작한다. Vite 설정도 바뀌었으므로 `C:\project\truckworks\frontend`에서 개발 서버를 다시 시작하고 화면을 새로고침한다. 백엔드는 기존대로 단일 worker를 사용한다.
3. 브라우저 개발자 도구 Network의 WS에서 `/api/factory/stream` 연결과 factory_state 메시지를 살펴본다. 화면 상태 수신을 위한 `/state`와 `/events` 요청이 300ms마다 반복되지 않아야 한다. 수동 도구/이력 GET은 별도다.
4. 차체 1개/20개 생산을 시작하고 설비・부품 이동・수량・이벤트가 함께 갱신되는지 확인한다. 일시정지 후 시간이 멈추며 heartbeat가 이어지고, 재개・고장・복구 뒤 상태가 반영돼야 한다.
5. 초기화 뒤 새 run_id・READY・소재 20개・새 실행 이벤트가 표시돼야 한다. 이전 실행의 이벤트가 섞이거나 늦은 제어 응답 때문에 돌아가면 안 된다.
6. 두 번째 탭을 열면 같은 실행 상태를 받아야 한다. 한 탭의 제어가 다른 탭에 반영돼야 한다. 동시 제어 충돌은 기존 HTTP 409로 안내한다.
7. 백엔드를 중단하면 연결 끊김 안내와 제어 비활성화를 확인한다. 재시작하면 수동 새로고침 없이 현재 실행을 다시 받아야 한다. 서버 재시작은 기존처럼 새 실행이며 DB 과거 기록을 실행 엔진으로 복원하지 않는다.
8. 화면을 나갔다 다시 열 때 이전 소켓의 재연결이 남지 않아야 한다. 개발 모드 StrictMode에서는 초기 연결이 한 번 정리되고 다시 열리는 모습이 있을 수 있다.

실패 시 WS 연결 상태・브라우저 메시지・서버 오류를 공유한다. 비밀키/환경변수 원문은 공유하지 않는다.

구현 방식은 [FastAPI WebSocket 안내](https://fastapi.tiangolo.com/advanced/websockets/)와 [Vite 프록시 옵션](https://vite.dev/config/server-options.html#server-proxy)을 참고했다.
